## 31. 版本演进路线

### 31.1 总览（每一版都有一个"能被别人验收的形态"）

| 版本 | 名称 | 一句话目标 | 引入技术 |
|---|---|---|---|
| **V0** | Bootstrap | **打开就有内容的可演示产品**（无 AI） | Spring Boot / MySQL / MyBatis-Plus / Flyway / Vue3 / Docker Compose |
| **V1** | Product MVP | 三条主线（内容/知识/数据）各自闭环 | Redis / 对象存储 / Spring AI / SSE |
| **V2** | Data Platform | 平台能**持续自动获得新内容** | Elasticsearch / Scheduler / Ingestion 全链路 / Vector |
| **V3** | Backend Engineering | 在真实压力下**站得住**，且每个优化有数据 | RabbitMQ / Prometheus+Grafana / k6 / 多级缓存 |
| **V4** | AI Platform | AI 从"能答"升级为"能研究、可评测、可防御" | Rerank / Research Agent / MCP / Eval / Moderation LLM |
| **V5** | Reliability | 故障发生时**能发现、能恢复、能复盘** | 故障注入 / 容量模型 / 性能回归 |

### 31.2 与你原规划的 3 处调整

1. **Provenance 前置到 V0**：`data_provenance` 表与 `content_item.provenance_id` 在 V0 就建好，即使 V0 只有种子数据也带来源标记。**理由：地基后补的代价是历史数据无法追溯。**
2. **V0 明确不做 AI**：把 V0 从"最小可跑"重新定义为"**启动即有内容生态**"。AI 是 V1 的增量。
3. **V3 新增"基线压测"作为第一个任务**：不用压测结果驱动的优化不允许进入代码。同时把"可观测性"提前到 V3（而非 V5），因为没有观测就无法定位瓶颈。

## 32. 每个版本的验收标准

> 验收标准必须**可执行、可复现、有明确通过条件**。以下每一条都是可勾选的检查项。

### V0 — Bootstrap

**目标**：任何人 clone 仓库 → 跑两条命令 → 10 分钟内看到一个"已经运营了一段时间"的平台。

| # | 验收项 | 通过条件 |
|---|---|---|
| V0-1 | 一键启动 | `make up && make bootstrap` 首次 ≤10 分钟，重复执行 ≤4 分钟，退出码 0 |
| V0-2 | 幂等 | 连续执行 bootstrap 两次，`content_item` / `post` / `user` 数量完全一致 |
| V0-3 | 首页非空 | 首页 7 个模块**全部有数据**（Trending ≥6 / Digest ≥1 / 推荐 ≥8 / 开源项目 ≥3 / 学习资源 ≥6 / 最新讨论 ≥10 / 数据源提示 ≥5 个源） |
| V0-4 | Bootstrap 自检 | 任一模块数据不足时 bootstrap 必须失败并打印具体缺口（不允许"静默空首页"） |
| V0-5 | 注册登录闭环 | 注册 → 登录 → 刷新 Token → 登出 → 旧 Token 失效，全流程通过 |

| V0-7 | 发帖闭环 | 发帖（Markdown + 1 张图）→ 出现在列表 → 详情正确渲染 → 无 XSS（含 `<script>` 的输入被消毒） |
| V0-8 | 评论/点赞 | 评论支持 2 层树；点赞幂等（连点 10 次计数只 +1） |

| V0-10 | 来源追溯 | 任一外部条目可跳转原链接并显示来源名与许可标记 |
| V0-11 | 通知 | 收到评论后通知列表 + 未读角标更新 |

| V0-14 | 文档 | README 包含：架构图、启动步骤、Demo 账号、已知限制 |

**V0 退出条件**：能给别人一个链接，让他自己注册并在 5 分钟内理解这个产品是什么。

### 33.2 硬依赖（不可违反）

## 36. 最终工程亮点（6 个 + 1 个可选）

**筛选原则：能被验证、能讲清取舍、解决真实问题。** 每个亮点按六段式描述；`验证` 均为"计划产出的实验/测试"，**未产出数据前不对外宣称具体数字**。

### 亮点 1 · 统一内容索引支撑跨源混合检索

| 维度 | 内容 |
|---|---|
| **实际问题** | 同一主题的内容散落在社区帖、采集资源、开源项目、用户空间四处，用户需要搜四次；且四类来源排序口径不一 |
| **定位依据** | 需求侧：4 个来源、1 个搜索框；技术上：多表 UNION 无法做跨类型相关性排序，MySQL 全文对中文长文效果差 |
| **原方案缺陷** | 各来源独立搜索 → 用户要切换 4 次；或 UNION 后按创建时间排 → 相关性完全丢失 |
| **新方案** | `ContentItem` 统一投影 + 单索引多 `item_type` + 分路召回（BM25/向量/标签/热度）+ RRF 融合 + 规则重排 + 分组聚合 |
| **技术取舍** | 放弃"每来源一个索引"（跨类型打分需二次归一化，更复杂）；放弃 V2 就上模型重排（延迟与成本不划算）；投影表带来最终一致性（延迟 <1s，可接受） |
| **验证** | `EX-015 搜索相关性对比`：单一来源 vs 统一检索的 `no_result_ratio` 与 `click@5`；延迟 P95 目标 <300ms |

### 亮点 2 · Scope-first Retrieval：权限前置的 RAG

| 维度 | 内容 |
|---|---|
| **实际问题** | AI 问答必须能用私有文档，但绝不能跨空间检索。常见的"先检索全库、生成后再过滤"存在数据泄漏路径 |
| **定位依据** | 安全需求（第 13 节）+ 检索质量需求：后置过滤会让无关的私有内容挤占 Top-K |
| **原方案缺陷** | ① 全库检索后过滤 → 私有内容已进 LLM 上下文；② Prompt 里叮嘱"别泄露" → 完全依赖模型自律 |
| **新方案** | `AuthorizedScope` 作为检索方法**必需参数**（编译期强制）→ 注入 ES `filter` 子句 → 与相关性打分同时发生；`autorizedWorkspaceIds()` 单一实现；一次请求内 scope 只算一次并记入 `ai_run` |
| **技术取舍** | ES filter 会略微降低召回多样性，但换来"检索链路中不存在未授权数据"；权限缓存 60s 换取性能，成员移除时主动失效 |
| **验证** | 集成测试集：跨空间检索用例全部返回空；`ai_run.scope_hash` 可审计；对照测试记录在 `EX-016` |

### 亮点 3 · 可恢复的文档处理异步管道

| 维度 | 内容 |
|---|---|
| **实际问题** | 上传大 PDF 时同步解析会打满线程、请求超时；解析中途崩溃会留下永久卡死的任务 |
| **定位依据** | 文档 P95 处理时长远大于 HTTP 超时；解析是 CPU + 外部调用混合负载 |
| **原方案缺陷** | 同步解析 → 请求超时、无法扩展、失败即丢；或简单异步 → 无状态可见性、无幂等、崩溃后任务卡死 |
| **新方案** | 状态机（PENDING→…→READY/FAILED）+ 条件更新领取任务（幂等）+ 超时任务扫描恢复 + 三级去重（L1/L2/L3）+ content_hash 秒传 + 删除后索引清理联动 + 进度推送 |
| **技术取舍** | 状态与进度落库带来额外写，换取可观测与可恢复；chunk 正文只进 ES（MySQL 只存元数据）换取库体积可控；不做加密 PDF 的破解（明确失败并给出原因） |
| **验证** | `EX-014 文档管道吞吐`：不同并发下的处理时长与队列深度；崩溃恢复演练（kill -9 worker 后任务自动恢复） |

### 亮点 4 · 社区读写的热点治理（有数据支撑的三层缓存 + 幂等写）

| 维度 | 内容 |
|---|---|
| **实际问题** | 爆款帖带来单 key 超高频读；点赞写放大与行锁竞争；热榜不能靠浏览量 |
| **定位依据** | 基线压测（EX-000）指出 Top 3 慢接口与 DB QPS 瓶颈 |
| **原方案缺陷** | 无缓存 → DB QPS 随 VU 线性上升至饱和；点赞直写 MySQL → `like_count` 行锁竞争，P99 恶化；热榜按累计浏览量排序 → 老内容长期霸榜且可刷 |
| **新方案** | ① 三级读路径：Caffeine → Redis → DB（Cache Aside + 逻辑过期 + TTL 抖动 + 空值缓存）② **热点探测**：滑动窗口识别热点 key → 提升为本地长 TTL 缓存 ③ 点赞：Lua 原子幂等 + 计数 INCR + outbox 异步批量落库 + 每日对账 ④ 热榜：**小时分桶 ZSet + 权重衰减 + 定时合并** |
| **技术取舍** | 接受最终一致（点赞在 Redis 宕机时可能丢少量）；**不做布隆过滤器**（ID 空间稀疏，收益低）；不做全量本地缓存（内存与一致性风险）；只优化 Top 3，不为"看起来专业"而全站上缓存 |
| **验证** | `EX-001/003/004/005/006`：QPS、P95/P99、DB QPS、缓存命中率 Before/After；点赞对账差异 = 0 |

### 亮点 5 · 合规可追溯的数据采集平台

| 维度 | 内容 |
|---|---|
| **实际问题** | 内容聚合产品最大的风险不是"抓不到"，而是"抓了不该抓的、说不能说的、抓了重复的、抓一次就崩" |
| **定位依据** | 版权合规要求 + 采集是唯一主动出站组件（最高危攻击面）|
| **原方案缺陷** | 每站一个脚本 → 无法维护；无去重 → 首页同内容刷屏；无 provenance → 无法追溯；URL 直连 → SSRF；固定频率 → 被封禁 |
| **新方案** | ① `DataSourceAdapter` 插件化（新增 RSS 源 = 一条配置）② **三级去重**（URL / content_hash / SimHash 近似）③ `ProvenanceGuard` 入库前合规断言 ④ **SSRF 防护链**（scheme→userinfo→端口→主机名→**DNS 解析后校验真实 IP**→白名单→**DNS pinning**→逐跳重校验重定向→体积/超时/压缩比限制）⑤ 条件请求增量 + per-host 令牌桶 + DLQ + 源自动熔断 |
| **技术取舍** | 官方 API/RSS 优先，网页抓取默认关闭（宁可少，不可越界）；许可不明只存 metadata；去重存 MySQL 而非 Bloom（可靠优先）；采集进程独立容器且不挂云凭证 |
| **验证** | SSRF 测试用例集（含十进制 IP、十六进制 IP、IPv6、重定向绕过）；`EX-018 采集吞吐与去重率`；连续 24h 无人值守成功率 |

### 亮点 6 · 把"不可信内容"当成一等公民的 AI 安全体系

| 维度 | 内容 |
|---|---|
| **实际问题** | 抓来的网页、用户上传的 PDF、工具返回结果里都可能藏指令；模型"看到"就等于"可能执行" |
| **定位依据** | 平台天然会处理大量外部不可信文本，且 AI 与权限系统深度耦合 |
| **原方案缺陷** | 直接把检索内容拼进 Prompt → 间接注入可诱导越权/泄露；只在 System Prompt 写"忽略注入" → 无强制力；模型输出的引用不校验 → 幻觉引用混入"权威"表述 |
| **新方案** | ① **内容信任分级**（TRUSTED / SEMI / UNTRUSTED）+ 服务端生成的分隔标记（用户无法伪造）② 工具结果同样标记 UNTRUSTED ③ **工具执行前重鉴权**（Agent 无独立权限身份，始终以用户身份执行）④ 引用校验（来源必须在本次检索集合内 + 引文相似度阈值 + 失败降级）⑤ 输出过滤 + 调用次数/Token/时长硬上限 + `ai_run` 全链路审计 ⑥ 红队用例集进 CI |
| **技术取舍** | 信任隔离会让 Prompt 变长（Token 成本上升），换取抗注入；引用校验会降低"回答流畅度"（部分场景降级为检索列表），换取"不编造"；不做专门的注入检测模型（成本不划算），用分层 + 校验覆盖 90% 场景 |
| **验证** | 30 条黄金集（含 10 条注入用例）注入抵抗率 ≥90%；越权工具调用用例 100% 拒绝；`EX-011 LLM 超时与熔断` |

### 亮点 7（可选）· 可解释推荐与数据驱动的 Topic Digest

| 维度 | 内容 |
|---|---|
| **实际问题** | 冷启动没有行为数据；黑盒推荐在内容站会引发"为什么给我看这个"的不信任 |
| **定位依据** | 冷启动阶段（无协同信号）；用户需要理解推荐来源 |
| **原方案缺陷** | 直接照搬深度学习排序 → 无数据可训；或纯热度排序 → 千人一面，新人反复看到同样内容 |
| **新方案** | 规则打分（标签兴趣 + log 互动 + 时间衰减 + 来源新鲜度 − 重复惩罚）+ **MMR 多样性重排** + **推荐理由展示**（"因为你收藏过 X"）；Digest 由真实采集数据驱动，无新内容则不生成 |
| **技术取舍** | 放弃短期个性化精度，换取可解释性与零训练成本；权重可后台调参并留痕 |
| **验证** | `EX-019`：推荐点击率 vs 纯热度的对比；Digest 溯源完整性检查（100% 条目可回溯来源） |

### 37.3 演示的三个"高光时刻"（重点准备）

1. **权限演示（6:00）**：直接输 URL 得到 404 + AI 引用中不出现私有文档 → 这是最难被质疑的能力。
2. **发布确认（7:00）**：把"私有内容绝不自动公开"做成产品交互，而不是文档里的一句话。
3. **注入抵抗（11:30）**：现场演示攻击被挡住，比任何架构图都有说服力。

### 37.4 失败兜底（必须准备，不能现场卡住）

| 风险 | 兜底 |
|---|---|
| LLM 超时/不可用 | 系统自动降级为"检索结果列表 + 提示"，演示话术改为"当模型不可用时我们这样降级" —— **把故障演示成能力** |
| 网络受限 | 提前缓存 3 个问题的回答（走同一套 UI，标注"离线缓存示例"） |
| 文档解析慢 | 准备一份已解析完成的文档；同时展示另一份的进度 |
| 采集失败 | 展示历史成功数据 + 失败任务的错误详情（**真实失败也是可信度**） |
| Bootstrap 失败 | 提前执行一次并保留数据；现场只演示"自检报告" |
