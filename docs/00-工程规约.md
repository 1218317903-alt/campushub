## 1. 产品定义（不得偏离）

CampusHub AI：面向高校学生和年轻学习者的 **AI 知识协作 + 内容社区 + 智能信息发现平台**。

## 2. 核心工程原则（优先级）

冲突时**从高到低**胜出：

```
业务正确 > 数据安全 > 可维护性 > 可测试性 > 可靠性 > 可观测性 > 性能 > 架构复杂度
```

**禁止为了显得高级而堆技术。** 具体禁令：

| 能用什么解决 | 就不要用什么 |
|---|---|
| 普通 Java 代码 | Agent |
| 确定性 Workflow | Agent |
| 模块化单体 | 微服务 |

## 4. 初期架构：Modular Monolith

### 4.1 模块边界

模块即业务域（第 1 节的 10 个）+ `common`。

**禁止**：

1. Controller 直接访问 Repository。
2. 跨模块随意直接操作其他模块的数据表。
3. 反向依赖、循环依赖。
4. `common` 变成万能垃圾桶。

**跨模块优先通过**：明确的 Application Service / Facade / Domain API。

### 4.2 微服务演进原则

**第一阶段禁止直接拆大量微服务。** 只有出现真实原因才考虑拆分：

- 独立扩容需求 · 资源模型明显不同 · 故障隔离
- 长任务与普通 API 相互影响 · 独立发布周期 · 独立安全边界

成熟后**优先**考虑拆分：Core Platform · AI Runtime · Data Ingestion · Notification。
**不建议出现十几个细碎服务。**

**每次拆分必须有 ADR**，回答 7 问：

1. 原单体结构出现了什么问题？
2. 为什么模块隔离还不够？
3. 为什么需要独立进程或服务？
4. 服务之间通过什么通信？
5. 数据由谁拥有？
6. 失败时如何处理？
7. 拆分增加了哪些复杂度？

## 5. 数据原则

### 5.1 来源必须可区分（落库字段，8 类）

`USER_GENERATED` · `USER_UPLOAD` · `SELF_CREATED` · `PUBLIC_API` · `OPEN_DATA` · `LICENSED_CONTENT` · `EXTERNAL_METADATA` · `SYNTHETIC_DEMO`

**Synthetic Data 只能用于**开发 / 演示 / 压测 / 测试，**不得冒充真实用户数据**。

### 5.2 外部数据优先级

官方 API → RSS / Atom → 开放数据 → Public Domain → 明确许可内容 → 公开元数据

**授权不明确的外部文章默认只保存**：`title` `description` `author` `source_url` `published_at` `tags` `metadata`。
**不要擅自保存完整正文。**

**所有公共内容必须保留 Data Provenance。**

## 6. Workspace 数据安全

Workspace 是**私域**。必须实现 **RBAC + Resource-Level Authorization**。

用户知道 `workspaceId` / `documentId` / `noteId`，**绝不代表拥有访问权限**。

以下操作**全部**必须执行资源级鉴权：
读取 · 修改 · 删除 · 下载 · 搜索 · RAG · Agent Tool Call

---

## 7. AI 数据隔离

**唯一允许的路径**：

```
User Identity
  ↓
Authorization
  ↓
Allowed Resource Scope
  ↓
Retrieval
  ↓
LLM
```

**禁止**：

```
全库 Vector Search → 拿到所有结果 → 最后在前端/后置过滤
```

权限必须在 **Retrieval 之前**或 **Retrieval Query 内**实现。

## 8. Agent 使用原则

### 8.1 能力阶梯（优先用左边）

```
普通代码 → Workflow → Tool Calling → Single Agent → Multi-Agent
```

**只有执行路径不确定时才使用 Agent。**

例：`Upload → Parse → Chunk → Embedding → Index` 属于 **Workflow，不要 Agent 化**。

### 8.2 Agent Runtime（后期建立，不是包装一次 LLM API）

必须设计：`orchestration` `state` `tool` `streaming` `cancellation` `budget` `loopguard` `security` `approval` `audit` `evaluation`

**Agent Run 状态**：`CREATED` → `RUNNING` → `WAITING_APPROVAL` / `CANCELLING` → `CANCELLED` / `COMPLETED` / `FAILED`

### 8.3 流式输出：统一 Agent Event Protocol

**不能只是传 token。** 至少支持：

`AGENT_STARTED` `STEP_STARTED` `TOOL_STARTED` `TOOL_FINISHED` `TEXT_DELTA` `APPROVAL_REQUIRED` `WARNING` `RUN_COMPLETED` `RUN_CANCELLED` `RUN_FAILED`

每个事件至少含 `runId` `timestamp` `type`；必要时含 `stepId` `toolName` `metadata`。客户端通过 **SSE** 接收。

### 8.4 取消机制

用户点击"停止生成"必须**真正取消后端 Agent Run**，不能只是前端停止渲染。

接口：`POST /agent/runs/{runId}/cancel`

取消后：停止后续 Tool 调用 → 尝试取消正在运行的 LLM 请求 → 释放资源 → 更新状态 → 记录 Audit。
需要考虑"用户关闭浏览器"的行为：短交互可自动取消；长 Research Task 可选择后台继续（需明确设计）。

### 8.5 死循环防护（必须全部实现）

1. Max Steps · 2. Run Timeout · 3. Tool Timeout · 4. Token Budget · 5. Tool Call Budget · 6. Repeated Tool Call Detection

**指纹算法**：`fingerprint = hash(toolName + normalizedArguments)`
相同指纹重复达到阈值 → 触发 `LOOP_DETECTED`。
**不能允许 Agent 无限调用搜索。**

### 8.6 Agent Security

**Agent 没有超级权限。** Tool 调用链必须是：

```
User → Agent → Tool Policy → Authorization → Business Service → Resource
```

Agent **不应该**直接获得：数据库密码 · API Secret · 管理员 Token · 云凭据 · 系统私钥。

**禁止设计** `executeAnySQL(sql)` 这类通用高危 Tool。
**优先业务 Tool**：`searchCommunity` `getWorkspaceDocument` `searchDiscover` `getRepositoryInfo`。

### 8.7 Tool Gateway（后期）

每次 Tool Call 携带：`userId` `agentId` `runId` `traceId` `resourceScope`

Gateway 执行：`Authentication → Authorization → Input Validation → Rate Limit → Execution → Output Filtering → Audit`

**Agent 不能绕过 Tool Gateway 直接调用 Repository。**

## 9. Prompt Injection 防护

### 9.1 以下全部属于 UNTRUSTED DATA

用户 Prompt · 用户上传文档 · RAG 文档 · Crawler 网页 · Community 内容 · Tool 输出

其中出现的 `"ignore previous instructions"` **不能成为系统指令**。

### 9.2 必须防

Direct Prompt Injection · Indirect Prompt Injection · Tool Output Injection · RAG Injection

### 9.3 关键认知

**真正安全必须来自：权限 · Tool Policy · 资源隔离 · 最小权限——而不仅是 System Prompt。**

---

## 10. 敏感信息与 DLP

### 10.1 至少识别

Password · API Key · Access Token · Bearer Token · Private Key · Database Connection String · Credential

### 10.2 用户请求"告诉我数据库密码"时

必须：**不调用任何敏感 Tool** → **拒绝敏感资源请求** → **写入安全审计**。

### 10.3 Output DLP

Output 在返回前经过 **DLP Scanner**；检测到 Secret → `Redact + Audit`。
**禁止日志中输出 Secret。**

---

## 11. 高风险操作与 HITL

若未来 Agent 能执行 `deletePost` `banUser` `deleteWorkspace` `modifyPermission` `sendBulkNotification` 等高风险操作，**不能仅由 LLM 自主执行**：

```
Agent → Policy Engine → High Risk → Human Approval → Execute
```

管理员能 `Approve` / `Reject`，**整个过程写入 Audit**。

---

## 12. Multi-Agent

**不能为了数量存在。** 优先实现 **Single Research Agent**。

只有出现以下情况才考虑拆分（Orchestrator / Research / Community / Repository / Reviewer）：

工具数量太大 · 职责冲突 · 上下文污染 · 权限差异 · 不同模型策略 · 独立扩容需求

**每个 Agent 必须有独立职责。不得出现多个 Agent 只是互相重复总结。**
**"不拆 Multi-Agent" 是合法结果。**

---

## 13. Crawler Security

Crawler URL **属于不可信输入**。必须防：

SSRF · localhost · 127.0.0.1 · ::1 · private IP · link-local · cloud metadata · DNS rebinding · 危险 redirect · 危险 scheme · 超大响应 · 压缩炸弹 · 异常 MIME · 无限跳转

**Crawler 不得拥有访问内部敏感系统的网络能力。**

---

## 14. 性能原则

**禁止提前宣称高并发。** 必须走：

```
Baseline → Pressure Test → Observe → Find Bottleneck → Optimize → Pressure Test Again
```

必须记录：QPS · P50 · P95 · P99 · Error Rate · CPU · Memory · GC · DB Pool · Redis · MQ Lag

**不允许伪造结果。** 未压测的必须写 `Not benchmarked yet`。

## 15. Git 版本管理（是项目的一部分，不是可选项）

### 15.1 禁止

**所有功能做完后一次性提交。** 必须保持**小步、可理解、可回滚**的提交历史。

### 15.2 分支约定

| 类型 | 命名 |
|---|---|
| 长期 | `main` · `develop` |
| 功能 | `feature/identity-auth` · `feature/community` · `feature/workspace` · `feature/document-pipeline` · `feature/discover` · `feature/search` · `feature/rag` · `feature/agent-runtime` |
| 修复 | `fix/xxx` |
| 安全 | `security/xxx` |
| 重构 | `refactor/xxx` |

**不要创建大量一天后就没人理解的随机分支。**

### 15.3 Commit 规范（Conventional Commits）

`feat:` `fix:` `refactor:` `test:` `docs:` `chore:` `perf:` `security:` `build:` `ci:`

**推荐写法示例**：

```
feat(identity): add refresh token rotation
feat(community): support nested comment replies
security(workspace): enforce document resource authorization
feat(agent): add SSE run event protocol
security(agent): block unauthorized tool calls
feat(agent): add repeated tool call loop guard
perf(community): cache hot post detail in redis
test(workspace): add cross-user IDOR tests
docs(agent): document agent runtime lifecycle
```

**禁止**：`update` · `fix bug` · `final version` · `修改代码` · `test` · `123`

### 15.4 提交粒度

一个 Commit **只解决一个主要问题**。

"Migration + Entity + Repository + 必要 Test" 可以属于同一个 Feature Commit；
但**不要把**"用户登录 + 论坛 + Redis + Agent + 前端首页"放在一个 Commit。

**每次提交前 6 步**：

1. 查看 `git diff`
2. 确认没有 Secret
3. 运行相关测试
4. 确认编译通过
5. 确认没有无关文件
6. 写清楚 Commit Message

### 15.5 禁止提交

`.env` · 真实 API Key · 数据库密码 · JWT Secret · 云凭据 · 私钥 · IDE 用户配置 · 日志文件 · 构建产物 · 大量临时文件

**提供 `.env.example`**，其中只保留变量名和示例。

### 15.6 Release / Tag

每个大阶段通过验收后创建 Tag：

`v0.1.0` 基础工程 · `v0.2.0` Identity+Community · `v0.3.0` Workspace · `v0.4.0` Data Platform · `v0.5.0` Search+RAG · `v0.6.0` Backend Engineering · `v0.7.0` Agent Runtime · `v1.0.0` 稳定完整版

每个 Release 记录：**Added · Changed · Fixed · Security · Known Issues**。维护 `CHANGELOG.md`。

### 15.7 ADR

重大设计决策写 `docs/adr/`，如 `0001-modular-monolith.md`。
ADR 至少包含：`Context` `Decision` `Alternatives` `Consequences`。

**不要事后伪造所有 ADR。做决策时写。**

### 15.8 数据库版本管理

任何 Schema 修改**必须通过 Flyway Migration**。

**禁止**手工改数据库然后忘记记录。Migration 必须进入 Git。
**禁止随意修改已经发布过的 Migration**；后续修改使用新的 Version。

## 16. 阶段开发流程

### 16.1 每阶段开始

1. `git status`
2. 阅读当前 README / architecture / ADR
3. 阅读当前模块结构
4. 创建对应 feature branch
5. 输出本阶段实施计划
6. 再开始修改代码

### 16.2 开发过程中

**小步提交。**

### 16.3 阶段完成

运行：`build` → `test` → `lint` → `integration test`；如适用：`security test` → `benchmark`

然后：更新 README → 更新 CHANGELOG → 补充 ADR → 最终阶段 Commit → 合并到 `develop`。
**通过稳定性验收后再合并 `main`。**

### 16.4 绝对禁止

- 自动 `force push`
- 擅自删除历史
- rewrite 公共分支历史

## 17. 阶段交付报告模板（**必须按此输出，不能只说"已完成"**）

```markdown
## Implemented              真正完成的内容
## Architecture Decisions   关键设计决策（含为什么这么选）
## Git History              本阶段 Commit：hash · message · 作用
## Database Changes         Migration 列表
## API                      主要新增接口
## Tests                    实际运行的命令 + 结果
## Security                 本阶段新增的安全保障
## Performance              有压测则给真实指标；否则明确写 Not benchmarked yet
## Known Limitations        未完成内容
## Technical Debt           技术债
## Next Phase Dependencies  下一阶段依赖
```

### 17.1 "Tests"一节的执行纪律（**硬性**）

**必须实际运行**：编译 · 单测 · 集成测试 · Lint · 构建。

- **失败不得说完成。**
- 无法运行的项要写清**为什么不能运行**，不允许含糊带过。
- 命令与结果必须是**真实粘贴**，不允许编造输出。

### 17.2 "Performance"一节的执行纪律

- 未做压测 → 必须明确写 `Not benchmarked yet`。
- 做了压测 → 必须给 Before/After 真实数据 + 环境说明 + 可复现脚本路径。

## 18. 阶段推进纪律（**最重要的一条**）

### 18.1 推进方式（2026-09-17 用户指令更新）

**授权连续执行：从 Phase 01 起一路推进到最后一个阶段，不再逐阶段停下来等确认。**

原"完成后停止、不得自动开发下一阶段"的约束**被用户显式解除**。
解除的是"停下来等确认"，**不是**任何质量约束 —— 下面 18.2 的准出条件一条都不能省。

调整原因：逐阶段等待确认的沟通成本，已经超过了它带来的风险控制收益。
但"连续执行"不等于"可以放松"：正因为没有人在每步之间核对，每步的自证必须更硬。

### 18.2 每阶段准出条件（**五条，缺一不可**）

1. **真实运行全量测试**：后端 `./mvnw -B verify`（单元 + 架构 + 真实 MySQL 集成），
   前端 `npm run build`。**失败不得说完成**；无法运行的项必须写明原因。
2. **小步提交**：Conventional Commits，一个 commit 只解决一个问题。禁止收尾时一次性大提交。
3. **打对应版本 tag**（Phase 02 → `v0.2.0`，以此类推）。
4. **更新文档**：`CHANGELOG.md` · `README.md`（进度） · `docs/architecture.md`（实现级说明是活文档）。
5. **输出 V2 十一节交付报告**（模板见 §17）。

### 18.3 仍然禁止的事

- **跳阶段、合并阶段**：不能为了"快点做完"把 Phase 05 和 06 合成一个。
- **提前实现更后面阶段的能力**：当前阶段不需要的中间件、抽象、扩展点，一律不写。
- **为了凑数而产生的代码**：接口永远返回固定值、TODO 占位、没人调用的"预留扩展点"。

### 18.4 何时必须停下来问

只有一种情况：**遇到无法自行决定、且会影响后续所有阶段的决策**。
典型如：需要外部账号或凭据、需要在互斥的技术路线之间做一次性取舍、
用户给出的约束互相冲突。此时**停下来问，不得猜测后继续**。

### 18.5 项目成型后的全量端到端验收（用户明确要求）

后期项目成型后，不能只靠"测试全绿"就宣布完成。必须**真正把整个项目跑起来**：

- 启动完整系统（数据库 + 后端 + 前端），按 README 从零部署一遍。
- **逐个走通所有对外接口**，记录实际请求与响应。
- **逐个走通前端功能**（列表 / 详情 / 发布 / 评论 / 上传 / 搜索 / 对话等），
  记录实际操作与结果。
- 目标是把"可审查的闭环"补完整 —— 任何只在代码里存在、从未被真正调用过的功能，
  都应当视为**未完成**，而不是"已完成但没测"。

### 18.6 平台可移植性（用户明确要求）

项目最终需迁移到 **Windows**。因此：

- 构建入口必须是**平台无关**的（Maven Wrapper + npm scripts + Docker Compose），
  不得让核心流程依赖 `make`、bash 或 POSIX 工具。
- 提供 Windows 下的等价入口脚本，并在文档中区分
  「已在 macOS 实测」与「未在真实 Windows 上验证」——
  **不得把未验证的适配写成已验证**。

### 18.7 对外表述纪律（用户明确要求）

本项目是一个**面向真实用户的产品**，其文档、README、注释、Commit message、
演示材料一律**不承载任何与求职 / 招聘 / 面试 / 简历相关的表述或暗示**。

技术写作要为了**说清工程判断**而写，不是为了给谁看而写。
判断标准很简单：**这句话如果没有第三方读者，是否仍然成立？**
若不成立（例如"面试时能讲清楚""写进简历站得住"），就不该出现。
