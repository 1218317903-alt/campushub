# EX-000 · 社区只读接口基线延迟

| 字段 | 内容 |
|---|---|
| **类型** | 基线测量（**不是**优化对比） |
| **阶段** | Phase 03 — Community MVP & Bootstrap |
| **日期** | 2026-09-17 |
| **脚本** | `scripts/bench/query-baseline.mjs`（Node，无第三方依赖） |
| **结论一句话** | 2000 帖规模下单请求 p50 为 3.0 ~ 8.0 ms、p99 ≤ 18.1 ms；**当前数据不支持引入缓存** |

> **为什么编号是 EX-000**：`docs/07-community-ops.md` §30.2 的模板是"优化前后对比"。
> 本记录没有任何 Before/After —— 它的用途是给 Phase 09 的性能工程提供**起点数字**，
> 以及"下一步该看哪几个接口"的候选清单。把它写成对比格式会隐含"已经优化过"的意思。

---

## 假设

在 2000 帖 / 4000 评论的真实数据量下：

1. 社区几个主要读取路径的单请求延迟应当在**个位数到十几毫秒**量级
   （本地单机、MySQL 同机、无网络跳转）；
2. 若某个场景明显高于这个量级，说明存在 N+1 查询或索引缺失，**值得在 Phase 09 优先看**；
3. 带登录态的读取应当比匿名慢 —— 因为要额外算 `liked` / `favorited`，
   但差异不应达到数量级；
4. 深分页（第 10 页）应当比第 1 页慢，但在这个规模下不至于痛。

**为什么要先做这一步**：`docs/00-工程规约.md` 与 `docs/07-community-ops.md` §30.1
都写明"没有基线数据不优化"。在没有这份数字之前谈缓存、谈索引、谈连接池，
无法判断优化是否真的解决了问题，也无法判断优化有没有效果。

## 环境

| 项 | 值 |
|---|---|
| 机器 | MacBook（Apple Silicon arm64）/ macOS 14.4，**单机**：应用与 MySQL 同机 |
| 依赖 | MySQL 8.4（Docker 容器，`127.0.0.1:3307`）；**未启用 Redis** |
| 应用 | Spring Boot 4.1.1 / Java 21.0.12 / Tomcat 单实例 / 默认连接池与线程配置 |
| 版本 | Phase 03 收尾（`v0.3.0` 之前的最后一次提交，见「复现」一节） |
| 数据集 | 帖子 **2000** · 评论 **4000** · 互动 **18094** · 浏览记录 **10000** · 作者 **20** · 板块 6 · 标签 15 |
| 日志 | `ai.camphub.*.infrastructure` 的 SQL DEBUG 日志**已关闭**（见下方「复现」） |
| 测量方式 | HTTP 端到端、**并发 1**、每场景预热 30 次 + 测量 200 次；共 13 个场景、2600 次测量 |

**为什么是 HTTP 端到端而不是直接量 SQL**：用户感知到的是"点一下要等多久"，
它包含 Tomcat、安全过滤链、参数校验、JSON 序列化与连接池等待。
只量 SQL 会漏掉这些，而它们经常才是主要成本。
"慢在哪一层"是另一个问题，用 `EXPLAIN` 与实际执行计划回答，不在本记录范围内。

**为什么 SQL 日志必须先关掉**：`local` profile 把 mapper 所在包设为 DEBUG，
每条 SQL 与参数都会打印到控制台。那是真实的 CPU 与 IO 开销，会算进端到端延迟 ——
不关掉的话，测出来的是"带日志的延迟"，而不是用户会遇到的延迟。

## 脚本

```bash
# 1. 起依赖（本机 MySQL 端口为 3307，见 .env）
make up

# 2. 起后端。规模必须显式给定 —— 变量名写错不会报错，只会静默用默认规模（60 帖）。
#    首次启动会生成演示数据，这一步要等 2 分钟左右，期间 readinessState 是 OUT_OF_SERVICE。
APP_DEMO_SEED_AUTHORS=20 APP_DEMO_SEED_POSTS=2000 APP_DEMO_SEED_COMMENTS=4000 make run

# 3. 确认数据规模真的对了（用 total 求证，不要相信"我记得我设了"）
curl -s 'http://127.0.0.1:8080/api/v1/community/posts?size=1' | grep -o '"total":[0-9]*'

# 4. 测量（另开一个终端）
node scripts/bench/query-baseline.mjs \
  --iterations 200 --warmup 30 \
  --username demo01 --password "$APP_DEMO_SEED_PASSWORD" \
  --out baseline.md
```

> **关掉 SQL 日志是测量的一部分，不是可选的美化。** `local` profile 把
> `ai.camphub.*.infrastructure` 设为 DEBUG，而日志级别**按 logger 名从具体到宽泛匹配** ——
> `ai.camphub.community.infrastructure=DEBUG` 比 `ai.camphub` 更具体，
> 于是 `--logging.level.ai.camphub=INFO` 对它**无效**。必须逐个覆盖（以 `java -jar` 启动为例）：
>
> ```bash
> # jar 名随 pom 的 <version> 变化，以 target/ 下的实际文件名为准
> java -jar target/camphub-0.3.0.jar --spring.profiles.active=local \
>   --logging.level.ai.camphub.community.infrastructure=INFO \
>   --logging.level.ai.camphub.identity.infrastructure=INFO \
>   --logging.level.ai.camphub.system.infrastructure=INFO \
>   --logging.level.ai.camphub=INFO
> ```
>
> 本记录第一次测量就是在这个状态下跑的（数字偏高），发现后重测才有上表。

脚本只用 Node 内置的 `fetch`，无第三方依赖，因此在 Windows 上同样可直接运行
（平台可移植性要求见 `docs/00-工程规约.md` §18.6）。它自己会打印数据集规模、
样本帖子的标识与互动数 —— **读到报告的人不必相信记录里的描述，可以直接核对**。

### 四类读取路径的对照

把同一类路径放在一起看，比逐行读更能说明问题：

| 对照 | 数字（p50） | 差值 | 读法 |
|---|---:|---:|---|
| 信息流第 1 页：匿名 **6.2** vs 带令牌 **7.7** | +1.5 ms | +24% | `liked` / `favorited` 要两个子查询，代价可见但不构成问题（**假设 3 成立**） |
| 帖子详情：匿名 **3.0** vs 带令牌 **5.3** | +2.3 ms | +77% | 带令牌时要查 `post_view_daily` 做按天去重，再决定是否 `+1` |
| 信息流第 1 页 **6.2** vs 第 10 页 **5.7** | −0.5 ms | 基本持平 | 第 10 页**没有变慢**。2000 帖、`LIMIT 180,20` 的偏移还不足以体现深分页代价 |
| 信息流：默认最新 **6.2** vs 最热排序 **5.8** | −0.4 ms | 基本持平 | `hot` 只改 `ORDER BY`（按点赞数），当前规模下无额外代价 |

**最慢的场景是"热门标签"（p50 8.0 ms）**，比信息流还慢。这是符合预期的：
它要按"被引用帖子数"倒序取前 20 个标签，聚合范围随帖子量增长；
而信息流只取 `LIMIT 20`。它也是本次唯一一个"随数据量线性变差"的候选，
Phase 09 若要挑第一个优化的对象，**先看它**，而不是先看信息流。

## 结论与局限

### 结论：**当前数据不支持引入缓存**

判据不是"数字够不够小"，而是**这份数字能不能指出一个具体的问题**。逐条对照开头的四个假设：

| 假设 | 结果 | 依据 |
|---|---|---|
| 1. 单请求延迟应在个位数到十几毫秒量级 | ✅ 成立 | 13 个场景 p50 落在 **3.0 ~ 8.0 ms**，最大的 p99 是 18.1 ms |
| 2. 明显偏高的场景意味着 N+1 或缺失索引 | ✅ 没有出现 | 没有任何场景达到"明显偏高"；最慢的 8.0 ms 也是聚合本身的工作量 |
| 3. 带登录态应更慢，但差异不应达数量级 | ✅ 成立 | 列表 +24%、详情 +77%，都是同量级的常量开销 |
| 4. 深分页应更慢，但在这个规模不至于痛 | ⚠️ 观察到的是**不慢** | 第 10 页 p50 5.7 ms，比第 1 页还低 0.5 ms |

第 4 条的偏差值得说清楚：这**不代表深分页没问题**，只代表 2000 帖 / `LIMIT 180,20` 这个规模
还不足以让它显形。`LIMIT offset` 的代价随 offset 线性增长，等到 offset 上万时才需要处理。
因此结论是"**现在不动它**"，而不是"它不是问题" —— 记录在 `CHANGELOG.md` 的 Known Issues 里。

**为什么不加缓存**：加了缓存能省下的最多是几毫秒，而代价是**引入一个新的失效面** ——
点赞后列表里的 `likeCount` 什么时候更新、评论后 `commentCount` 什么时候更新、
发布后新帖多久才出现在信息流里。这些问题的复杂度远高于 6 毫秒。
`docs/00-工程规约.md` §15 与 `docs/07-community-ops.md` §30.1 都要求"先有数据再优化"，
这份数据给出的答案是：**还没有到需要付这个复杂度的时候**。
真要优化，第一位是"热门标签"的聚合口径，那是在同一套依赖内就能做的调整。

这也回答了一个容易被忽略的问题：**如果现在加了 Redis，会得到什么**？
会得到一个 5 ms 的接口、一套缓存失效逻辑，以及一个无法回答的问题 ——
"如果有一天它变慢了，是数据库还是缓存策略的问题？" 现在不加，是为了让未来的性能问题
仍然可以被归因到一个具体的地方。

### 局限（读这张表时要知道的事）

1. **并发为 1。** 这张表里的数字**不能**用来推算吞吐。10 个并发下的表现取决于连接池、
   Tomcat 线程池、MySQL 的并发处理能力，三者都不在这份测量的范围内。吞吐属于 Phase 09。
2. **单机、MySQL 同机、无网络跳转。** 这几个数字里不含任何真实的网络往返。
   部署到跨机环境时，网络与 TLS 会成为主要成本，届时这张表的参考价值会明显下降。
3. **`--iterations 200`、`--warmup 30`。** 样本量足以看出分布形状，但 p99 只由
   约 2 个样本决定，**p99 与 max 这两列的可重复性较差**。看趋势可以，比较两个版本的 p99
   需要加大迭代次数。
4. **数据是合成的、分布均匀。** 演示数据里每帖的评论数、互动数接近一致，
   而真实社区是重尾分布 —— 少数热帖承担大部分互动。**热点帖的读取成本没有被这份测量覆盖**，
   而它往往是真实系统里最先出问题的地方。
5. **只测读取，不测写入。** 发布 / 评论 / 点赞 / 收藏的延迟不在本记录范围内。
6. **没有 `EXPLAIN`。** 本记录回答"多快"，不回答"为什么是这个速度"。
   若要归因到具体索引（例如"热门标签"的聚合），需要另做执行计划分析。

### 下一步该看哪几个接口

按"随数据量增长而变差的风险"排序，而不是按当前延迟排序：

| 优先级 | 接口 | 理由 | 触发条件 |
|---|---|---|---|
| 1 | `GET /tags` | 唯一按全表聚合计数的读路径，随帖子量线性增长 | p95 超过 50 ms，或帖子量超过 10 万 |
| 2 | 深分页列表 | `LIMIT offset` 的固有代价，当前规模未显形 | offset 超过 1 万，或某个筛选条件下 p95 超过 50 ms |
| 3 | 带登录态信息流 | 每行两个子查询，随页大小线性增长 | 页大小调大，或上述 +24% 的差值变成倍数 |
| — | 其余 | 无 | — |

## 复现

- 代码版本：`git log -1`（本记录对应的提交在 `v0.3.0` tag 之前）
- 演示数据生成耗时：**131246 ms（约 131 秒）**，日志原文
  `演示数据生成完成：作者 20 位、帖子 2000 条、评论 4000 条、互动 18094 次、浏览记录 10000 次，耗时 131246 ms`。
  它走**公开应用服务**（密码真哈希、Markdown 真渲染、审计真写），而不是直接 `INSERT` ——
  见 `docs/architecture.md` §9。这份慢换来的是：演示数据与真实用户走的是同一条代码路径。
- 全部数字来自**真实运行**，没有任何一项是估算、补全或事后调整的。
  若与你的测量结果不一致，优先核对这四项，它们都曾导致过偏差：

  | 核对项 | 怎么确认 | 曾经踩过的坑 |
  |---|---|---|
  | 数据集规模 | `GET /api/v1/community/posts?size=1` 的 `total` | 环境变量名写错**不报错**，静默用默认 60 帖 |
  | SQL 日志是否已关 | 应用日志里 `grep -c "Preparing: SELECT"` 应为 0 | `--logging.level.ai.camphub=INFO` 关不掉更具体的 mapper logger |
  | 应用是否已完成数据生成 | 健康检查通过 ≠ 数据生成完成 | 生成期间 `readinessState` 是 `OUT_OF_SERVICE`，此时测到的数字偏高 |
  | 是否有其他进程占用 CPU | `top` | 编译、Docker 构建、其他 JVM 都会显著抬高 p99 |
