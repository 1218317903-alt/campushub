## V0 完成定义（DoD）

一个 Story 只有全部满足才算完成：

- [ ] 代码通过评审，符合模块边界（ArchUnit 通过）
- [ ] 有对应单元测试或集成测试（权限类必须集成测试）
- [ ] 权限：明确该接口是公开 / 需登录 / 需空间权限，并有测试覆盖
- [ ] 日志：关键路径有结构化日志，含 `traceId`
- [ ] 错误：异常有明确业务码与用户可见文案
- [ ] API：OpenAPI 注解完整，前端可用
- [ ] 前端：有加载态、空态、错误态（**空态不许白屏**）
- [ ] 无需人工干预即可在干净环境跑通

## V0 依赖边界（**先于一切编码生效**）

> 依据 `02-architecture.md` §34.1 的引入节奏。**V0 只依赖 MySQL 一个外部组件。**

| 组件 | V0 | 引入版本 | 不引入时，V0 靠什么满足 |
|---|---|---|---|
| MySQL 8.4 | ✅ 必需 | V0 | —— |
| **Redis** | ❌ 不引入 | **V1**（会话/计数）、V3（多级缓存 / 热榜 / 限流） | 未读数用 `notification` 表 `COUNT`；点赞幂等用**唯一索引**；令牌撤销用 `user.token_version`（JWT 内 `ver` 声明）；限流用进程内令牌桶（V0 单实例足够） |
| MinIO / 对象存储 | ❌ 不引入 | V1 | V0 帖子配图存本地卷 + 静态映射（**已知技术债，V1 迁移 MinIO**） |
| Elasticsearch | ❌ | V2 | MySQL 全文索引 + LIKE 兜底 |
| MQ | ❌ | V3 | 事务性 Outbox 表 + 定时轮询唤醒 |
| LLM / Spring AI | ❌ | V1 | —— |

**为什么本机已跑着 Redis，V0 却不起它**：`desk` 环境已提供 Redis 7.4.11（含 AOF），V1 引入时**零准备成本**。V0 不在 `compose.yaml` 中声明它，是为避免"依赖存在但无正当用途"——这正是本项目的宪法 (`00-工程规约.md`) 所禁止的"为技术栈而拼装"。

> **修订记录（2026-09-17）**：本文档原 E0-3 写"启动 MySQL + Redis + MinIO"、E7-3 写"Redis 计数"，与 `02-architecture.md` §34.1 的"V0 不引入 Redis"**互相矛盾**。现按 §34.1 统一为"V0 仅 MySQL"。**V0 编码前必须先确认本节边界。**

## V0 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| ES 未引入导致搜索效果差 | 演示时"搜不到东西" | V0 用 MySQL FULLTEXT + 标签 + 标题 LIKE 三重兜底；明确标注"V2 升级为 ES" |
| 种子数据显假（一看就是编的） | 首页生态感崩塌 | 人设化用户 + 分类分布 + 长文/代码块/图片混排 + 演示徽章公开标注 |
| 权限三层防线复杂度高，拖慢进度 | 迭代 2 延期 | 第 3 层拦截器可在迭代 2 末尾补，前两层先行（但**必须在 Community 开放前完成**） |
| Bootstrap 首次耗时长（镜像拉取） | Demo 前紧张 | 提供 `--skip=crawl` 离线模式；镜像预拉取脚本 |
| 前端工作量大 | 首页迟迟不可见 | 迭代 2 先做"丑但可用"的页面，迭代 3 集中做首页视觉 |
| 单人开发容易在细节上迷失 | 延期 | 每个迭代以**可演示形态**为出口标准，不做无演示价值的内部重构 |
