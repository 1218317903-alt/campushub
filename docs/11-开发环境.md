### 2.1 本机 npm 安装必须绕开托管 `NODE_OPTIONS`（2026-09-17 实测）

**现象**：在 WorkBuddy 托管环境中直接执行 `npm install` 会失败：

```
npm error code CODEBUDDY_BROKER_DENY
npm error Brokered host mkdir requires an available runtime file rule
```

**根因**：托管运行时通过 `NODE_OPTIONS` 注入了一个文件系统代理 shim
（`node-brokered-fs-shim.cjs`），它把 node 的 `fs` 操作转交给宿主做策略判定。
npm 在 reify 阶段的 `moveFile`（`@npmcli/fs`）会并发对 `node_modules/<pkg>` 执行
`fs.promises.mkdir`，该操作未命中代理的文件规则，于是被拒绝。

**已验证的排除项**（避免误判为网络或权限问题）：

- 单独用 node 执行 `fs.mkdirSync` / `fs.promises.mkdir`（含 `recursive: true` 的深层路径）**均正常**；
- 换个缓存目录（`--cache` 指向项目内）**无效**，仍报同一错误；
- 包本身下载正常 —— 失败发生在**落盘移动阶段**，不是网络问题。

**对策**：安装依赖时把 `NODE_OPTIONS` 置空，使 npm 不加载该 shim。

```sh
cd frontend
NODE_OPTIONS="" npm install
NODE_OPTIONS="" npm run build
```

> 同时建议把 npm 缓存指向项目内目录，避免污染用户级缓存：
> `NODE_OPTIONS="" npm install --cache "$(pwd)/.npm-cache"`
> （`.npm-cache/` 已被 `frontend/.gitignore` 忽略。）
>
> **这是本机托管环境的限制，不是项目本身的问题** —— 仓库内容在普通开发机上无需此操作。

## 3. 环境变量加载（**每条命令都要注意**）

配置在 `~/Desktop/desk/env.sh`：

```sh
export DESK_DEV_HOME="$HOME/Desktop/desk"
export JAVA_HOME="$DESK_DEV_HOME/runtimes/jdk/Contents/Home"
export MAVEN_HOME="$DESK_DEV_HOME/runtimes/maven"
export PATH="$DESK_DEV_HOME/bin:$JAVA_HOME/bin:$MAVEN_HOME/bin:$DESK_DEV_HOME/runtimes/python/bin:$DESK_DEV_HOME/apps/Docker.app/Contents/Resources/bin:$PATH"
export SSL_CERT_FILE="/etc/ssl/cert.pem"
```

- 该文件已被写入 `~/.zshrc`，**登录终端自动生效**。
- **但自动化工具的非登录 shell 不会加载它**。因此所有需要 Java / Docker / mysql / redis-cli 的命令，**必须先手动加载**：

```sh
source "$HOME/Desktop/desk/env.sh"
```

未加载时的典型症状：`java -version` 报 "Unable to locate a Java Runtime"；`which docker` 找不到。**这不是环境没装好，而是 PATH 没加载。**

> 注：`~/.zprofile` 与 `~/.profile` 里已有 Docker 的 PATH 追加（`~/.docker/bin`），但非登录 shell 不读这两个文件。

### 5.1 为什么"不需要登录"（2026-09-17 实测确认）

容易混淆的是三个不同层面的"登录"，它们都被**无需登录**，但原因各不相同：

| 层面 | 是否需要 | 原因 |
|---|---|---|
| Docker Hub / Docker Desktop 账户 | **不需要** | 所需镜像 `mysql:8.4`、`redis:7.4` **已在本地镜像库**，不触发远程拉取，因此不涉及 registry 认证。（本机 `registry-1.docker.io` 实测不可达，但这对本项目无影响——镜像已就位） |
| MySQL / Redis 的"登录" | **不需要交互式登录，但每次连接有密码认证** | 它们是本地容器，不是云控制台。认证发生在**每次连接握手**：密码已在容器创建时由 `.env` 注入（`MYSQL_PASSWORD` / `REDIS_PASSWORD`），应用读取环境变量即可。不存在"先在浏览器登录再使用"的环节 |
| 数据库图形客户端（Navicat 等） | **不需要额外安装** | desk 已提供 `mysql` / `redis-cli` 命令直连容器内客户端，自动带凭据 |

**实测证据（本轮真实执行）**：

```
MySQL  : 8.4.11 · 当前用户 dev@% · 库 devdb · utf8mb4 / utf8mb4_0900_ai_ci
         time_zone=SYSTEM · 隔离级别 REPEATABLE-READ
Redis  : 7.4.11 · PING → PONG · appendonly=yes · SET/GET 读写正常
容器   : desk-dev-mysql-1 / desk-dev-redis-1 均 Up (healthy)
```

**关键细节（会影响后续实现，务必记住）**：

- **Redis 已开 AOF**（`--appendonly yes`）→ 重启不丢数据；但这也意味着**压测前需清库**，否则历史键会污染基线数据。
- **MySQL 隔离级别是 MySQL 8 默认的 `REPEATABLE-READ`**，不是 READ-COMMITTED。这对"点赞计数""热榜统计"类并发写的可见性有直接影响，V3 压测时要按真实隔离级别分析，不能默认 READ-COMMITTED。
- **MySQL 默认 `time_zone=SYSTEM`** → 依赖容器时区。应用侧必须显式指定时区（JDBC URL 带 `serverTimezone`/`connectionTimeZone`），否则"发布时间/时间衰减排序"会出现时区错位。这是本项目**排序类功能的高风险点**。
- **端口仅绑 `127.0.0.1`**，且用户名是 `dev@%`（host 为通配）→ 本机可达、局域网不可达。

### 7.2bis `github.com` 曾经"不可达" —— 这是一次错误结论，已更正

**2026-09-17 记录（错误）**：曾写下"经代理的 Web 请求返回 `000`；
`git ls-remote https://github.com/...` 稳定报 `CONNECT tunnel failed, response 502`，
因此**本机不能把 `github.com` 当 git remote**"。

**同日更正**：这个结论是错的。`502` 确实存在，但根因不是网络不通，而是
**命令跑在 WorkBuddy 沙箱代理之下**（`HTTP_PROXY` 等环境变量被注入为
`http://127.0.0.1:62538`），而**沙箱代理对 `github.com` 的域名策略拒绝了 CONNECT 隧道**。

本机另有一个正常的代理在跑：**ClashX，`127.0.0.1:7890`**（系统代理也指向它，
HTTP / HTTPS / SOCKS 三协议同一端口）。指向它之后 GitHub 完全正常：

```
curl -x http://127.0.0.1:7890 https://github.com          → HTTP 200
git ls-remote https://github.com/git/git HEAD             → 成功（复测 3 次一致）
```

**教训（值得记住）**：诊断"网络不可达"之前，必须先确认**当前命令走的是哪条出口**。
`curl` 与 `git` 都会默默读取 `*_PROXY` 环境变量，因此"我测过了"可能与
"实际使用时"走的不是同一条路径。把出口搞错，就会把"沙箱策略限制"误判为
"网络不通"，进而做出错误的技术决策（例如放弃 GitHub 改用其它托管）。

### 7.4 Git 访问 GitHub：绕过沙箱代理

沙箱代理只影响**被沙箱包裹的命令**。`git` 的解决方式是给 `github.com`
单独指定代理，且**只对 GitHub 生效**，不影响 gitee 等本来就可达的站点：

```sh
git config --global http.https://github.com.proxy     http://127.0.0.1:7890
git config --global http.https://api.github.com.proxy http://127.0.0.1:7890
```

写入后 `~/.gitconfig` 中会出现（URL 级作用域，不是全局 http.proxy）：

```ini
[http "https://github.com"]
	proxy = http://127.0.0.1:7890
[http "https://api.github.com"]
	proxy = http://127.0.0.1:7890
```

验证：`git ls-remote https://github.com/git/git HEAD` 能返回 commit id。
实测 `git` 的 `http.<url>.proxy` 配置**优先于**环境变量里的 `HTTPS_PROXY`，
因此即使沙箱注入了代理变量，GitHub 仍走 ClashX。

> **前提**：ClashX 必须在运行。若它没开，GitHub 会退回不可用状态，
> 而 gitee 不受影响（走的是另一条路径）。
>
> **不想要这个配置时**：
> `git config --global --unset http.https://github.com.proxy`

### 7.5 Testcontainers 的 ryuk 镜像：用户级配置，**不在仓库内**

Testcontainers 启动时会拉取 `testcontainers/ryuk`（测试结束后负责回收容器）。
本机 Docker Hub 不可达（见 7.2），拉取会失败，且失败信息看起来像"测试代码有问题"，
实际是环境问题。因此本机需要把 ryuk 指向本地已有的 tag：

```sh
# 一次性准备镜像（走镜像代理）
docker pull docker.m.daocloud.io/testcontainers/ryuk:0.11.0
docker tag  docker.m.daocloud.io/testcontainers/ryuk:0.11.0 testcontainers/ryuk:0.11.0
```

**这个适配放在用户级 `~/.testcontainers.properties`，不进仓库：**

```properties
ryuk.container.image=testcontainers/ryuk:0.11.0
```

为什么必须放用户级而不是仓库内（这一点最初做错了，已修正）：

- 这是**本机专属的环境适配**，对其它机器毫无意义。放进仓库等于让每个克隆者
  都被固定在这个（较旧的）ryuk 版本上。
- Testcontainers 构建期会明确警告该替换机制
  `deprecated and will be removed in the future`。机制一旦移除，
  仓库里这个文件就成了死配置 —— 而本机恰恰依赖它才能跑集成测试。
- 放在用户级，仓库保持干净，能直连 Docker Hub 的机器**零配置**即可运行集成测试。

验证方式：删掉仓库内文件后重跑集成测试，ryuk 替换仍然生效、测试全部通过。

### 7.5bis MinIO 镜像：Docker Hub 上已下架，必须用 quay.io

`S3ObjectStorageIT` 需要一台真实 MinIO。**`minio/minio` 在 Docker Hub 上已经不存在了**
（2026-09-18 实测：`/v2/repositories/minio/minio/` → `HTTP 404 object not found`），
MinIO 把社区镜像迁到了 quay.io。

这个坑的表现极具迷惑性：**本机绿、CI 红**。因为本机早先已经把 quay 的镜像打过一次
同名 tag（`docker tag quay.io/minio/minio:latest minio/minio:latest`，两者 ID 相同，
可用 `docker images` 直接看出来），于是旧引用在本机"能用"；
而干净的 CI runner 上没有这份人工 tag，拉取直接失败。

现在的引用是**固定的 release**（钉版本的理由与 `mysql:8.4` 一致）：

```text
quay.io/minio/minio:RELEASE.2025-09-07T16-13-09Z
```

需要试新版本时用 `-Dtestcontainers.minio.image=quay.io/minio/minio:<other>` 覆盖，
不要把默认值改回会漂移的 `latest`。

**教训（值得单独记）**：本机"能跑"不等于别人"能跑"。
判断某个容器依赖是否真的可复现，要看**引用的镜像在公开仓库里能不能拉到**，
而不是看本机 `docker images` 里有没有 —— 人工打过 tag 的镜像与拉下来的镜像，
在 `docker images` 里长得一模一样。

### 7.6 `SERVER__PORT` 会把后端挤到随机端口上（2026-09-18 实测）

**现象**：`make run` 之后 `http://127.0.0.1:8080` 连不上，而日志里 Tomcat 报的是另一个端口：

```
Tomcat started on port 62060 (http) with context path '/'
```

**原因**：运行环境会向子进程注入一个 `SERVER__PORT`（它的值与同一环境里
`CODEBUDDY_SERVICE_PROXY_URL` 的端口一致，即 **62060**）。Spring Boot 的宽松绑定
（relaxed binding）把 `SERVER__PORT` 识别为 `server.port`，而**操作系统环境变量的优先级
高于 `application.yml`** —— 于是 `${SERVER_PORT:8080}`（以及 `.env` 里的 `SERVER_PORT=8080`）
被静默压掉。两者只差一个下划线：`SERVER_PORT` 是配置项，`SERVER__PORT` 是环境的注入。

**确认方式**（不靠猜，直接读进程环境）：

```sh
ps -p <后端 pid> -wwwE | tr ' ' '\n' | grep -E '^(SERVER__PORT|SERVER_PORT)='
```

**做法**：本地起后端时**显式指定端口**。命令行参数优先级最高，能压过注入的环境变量：

```sh
./mvnw -B spring-boot:run -Dspring-boot.run.arguments=--server.port=8080
```

（`make run` 走的是不带该参数的 `spring-boot:run`，因此在被注入该变量的环境里
会出现"配置写了 8080、应用跑在别的端口上"且**没有任何报错**。
前端 `make fe-dev` 的 `/api` 代理指向 8080，两者不一致时的表现是页面所有请求 502。）

### 7.7 Vite 只监听 `localhost`（本机解析到 `::1`）

`npm run dev` 打印的是 `http://localhost:5173/`，而它**没有**监听 `127.0.0.1:5173`：

```sh
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:5173/     # 000
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:5173/     # 200
```

本机的 `localhost` 解析到 `::1`，Vite 默认就绑在那上面。

**对验收脚本的影响**：`scripts/e2e/browser-check.mjs` 的默认 `--base-url` 曾经写成
`http://127.0.0.1:5173`，于是脚本第一步就失败，而错误看起来像是页面没渲染出来 ——
真正的原因在另一层（监听地址），中间没有任何提示。现已改为 `http://localhost:5173`。
需要显式绑 IPv4 时用 `npm run dev -- --host 127.0.0.1`。

### 7.8 切换分支前先停 dev server：它会重写一个**被 git 跟踪**的文件

`frontend/src/components.d.ts` 由 `unplugin-vue-components` 生成、但需要入库
（`strictTemplates` 依赖它）。dev server 在运行时会**按当前源码树重写这个文件**，
于是：

- 切到另一个分支后，工作树里的 `components.d.ts` 与目标分支不一致 → 文件变成"已修改"；
- 此时 `git merge` 会直接**中止**：

  ```text
  error: Your local changes to the following files would be overwritten by merge:
          frontend/src/components.d.ts
  ```

  这个报错很容易被误读成"分支之间有冲突"，而实际上只是一个生成物被工具改写了。

**做法**：切分支/合并前先停掉 dev server；已经出现时先
`git checkout -- frontend/src/components.d.ts` 再操作（该文件的内容由源码树决定，
丢弃本地改动不会丢失任何信息）。

**另**：上一次运行残留的后端/前端进程会占着 8080 / 5173，导致新进程静默换端口
（表现为前端代理 502）。起新进程前先确认没人占：

```sh
lsof -nP -iTCP:8080 -sTCP:LISTEN -t     # 有输出说明被占用
lsof -nP -iTCP:5173 -sTCP:LISTEN -t
```
