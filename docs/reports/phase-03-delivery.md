## Implemented

### 社区内容域

- **`community` 模块**（领域 / 应用 / 接口 三层，与 `identity`、`system` 同级）：
  - 领域：`Post` · `PostSummary` · `PostDetail` · `Comment` · `Category` · `Tag` · `TagAssignment` ·
    `MarkdownRenderer` · `Slugifier` · `PostSort`
  - 应用：`PostService` · `CommentService` · `ReactionService` · `TagService`
  - 接口：`PostController` · `CommentController` · `CommunityController` ·
    `PostSortConverter` · `PageResponse` · `CurrentUser`
- **功能范围**：板块 · 标签 · 帖子（发布 / 编辑 / 软删除）· 两级评论与回复 ·
  点赞 · 收藏 · 浏览计数；列表支持板块筛选、标签筛选、`latest` / `hot` 排序与分页。

### 演示数据（`bootstrap` 组装点）

- `DemoSeedRunner` · `DemoContentLibrary` · `DemoSeedProperties` · `DemoCommentPlan`。
- **只调用各模块的公开应用服务**（注册 / 发帖 / 评论 / 点赞），不直接 `INSERT` 数据表 ——
  因此密码会被真正哈希、Markdown 会被真正渲染与净化、审计会被真正记录。
  演示数据与真实用户走的是**同一条代码路径**。
- 默认关闭；**显式拒绝在 `prod` profile 下执行**；按"库里有没有帖子"判断幂等；
  规模由 `app.demo-seed.*` 配置。

### 前端

- 社区信息流（筛选条件写回 URL）、帖子详情、发布 / 编辑、我的收藏、登录与注册（同页）。
- `auth` store 与 `http.ts` 的「令牌过期 → 刷新 → 重试一次」链路。
- 组件 `PostCardItem` · `CommentThread` · `PasswordInput`；工具 `utils/datetime` · `utils/form`。
- 全部视图为**路由级懒加载**。
- **应用外壳补齐**（本阶段收尾时发现并修复，见下）：顶栏加入社区导航与登录 / 登出入口，
  版本号改为从 `/api/v1/system/info` 读取。

### 测量与决策记录

- `scripts/bench/query-baseline.mjs`：可复现的社区只读接口延迟测量脚本（Node 内置 `fetch`，
  无第三方依赖，Windows 可直接运行）。

### 端到端验收中发现并修复的真实缺陷（§18.5）

本节列出的是**功能已经写好、但按真实用户路径走不通**的问题。它们全部由"把系统跑起来"暴露，
而不是由测试套件暴露 —— 这一点本身是本阶段最值得记录的一条经验。

| # | 缺陷 | 后果 | 为什么测试没抓到 |
|---|---|---|---|
| 1 | **应用外壳没有通往社区的任何入口** | 顶栏导航只有「概览」一项，社区与"我的收藏"无法进入 | 测试直接请求路由路径，不经过导航点击 |
| 2 | **没有任何 UI 能触发登出** | `auth.logout()` 存在却无人调用，用户登录后无法退出 | 同上：接口测试直接调用登出端点 |
| 3 | **顶栏硬编码 `v0.1.0 · Phase 01`** | 社区上线后版本徽标仍停在上一阶段，是**看起来正常的错误信息** | 没有任何断言检查页面上的版本文字 |
| 4 | `?sort=hot` / `?sort=latest` 返回 **400**（已在阶段内修复并记入 CHANGELOG） | 前端所有带排序的列表请求失败 | 集成测试里一次都没出现过 `sort` 参数 |

修复 1~3 后，前端真实浏览器流程由 22/24 转为 **24/24 全绿**（其中「登出清空令牌」与
「未登录访问我的收藏被守卫拦回登录页」两项正是前两条缺陷的直接体现）。

## Architecture Decisions

| 决策 | 选择 | 为什么 | 记录 |
|---|---|---|---|
| 互动计数放哪 | 内联在 `post` 表，**不预先拆 `content_stats`** | 计数就是 `COUNT(*)` 的结果；提前拆表等于凭空多一处必须同步的冗余，而当前没有任何测量数据说明它是瓶颈 | `docs/adr/0004` |
| 内容渲染边界 | 写入时渲染 + 净化一次，`body_md` 为**事实来源**，`body_html` 为读路径快照 | 读路径不解析 Markdown；代价是净化白名单的修复不自动作用于历史 HTML（已记入 Known Issues，回填路径确定） | `docs/adr/0005` |
| 互动幂等靠什么 | **主键 `(user_id, post_id, type)`**，捕获 `DuplicateKeyException` 判断"是否真新增" | 计数的正确性不依赖业务代码的判断；重复点赞不可能写出第二行 | `V3__community.sql` |
| 评论层级 | 严格两层，`parent_id` 自引用 + `ON DELETE CASCADE`；**刻意不存 `root_id`** | 在两层约束下 `root_id` 与"回复的 `parent_id`"恒等。层级规则由服务层保证并被集成测试钉住 | `V3__community.sql` |
| 浏览计数 | 明细表 `post_view_daily` 负责按天去重，汇总落 `post.view_count` | "谁看过"与"看过多少次"是两个问题，混在一张表里会让去重查询变成写放大的来源 | `V3__community.sql` |
| 帖子索引是否带 `deleted_at` | **不带** | 作为末列无助于过滤，作为首列会破坏有序扫描；正常运营下删除率是个位数百分比 | `V3__community.sql` |
| 安全放行粒度 | **逐条列出**社区 GET 端点，不放行 `/api/v1/community/**` | 整段放行会让"以后新增的接口"默认公开；逐条列出使新接口默认需要认证 | `SecurityConfig` |
| 归属校验返回什么 | **统一 404 而非 403** | 403 等于承认"这条资源存在"，泄漏了本不该给出的信息 | `PostService` 类注释 |
| 本阶段是否引入 Redis | **不引入** | 基线数据显示读取 p50 为 3.0~8.0 ms；缓存能省几毫秒，代价是引入点赞后计数何时更新这类**无法归因**的新失效面 | `EX-000` · `CHANGELOG` |

## API

新增 `/api/v1/community` 接口（✅ 表示匿名可访问，其余需登录）：

| 方法 | 路径 | 公开 | 说明 |
|---|---|:--:|---|
| GET | `/categories` | ✅ | 板块列表 |
| GET | `/tags` | ✅ | 热门标签（按被引用帖子数倒序，最多 20 个） |
| GET | `/posts` | ✅ | 帖子列表；支持板块 / 标签筛选、`latest` / `hot` 排序、分页 |
| GET | `/posts/{publicId}` | ✅ | 详情；带令牌访问记录一次浏览（同用户同天只计一次） |
| POST | `/posts` | — | 发布 |
| PUT | `/posts/{publicId}` | — | 编辑（仅作者） |
| DELETE | `/posts/{publicId}` | — | 删除（软删除，仅作者） |
| GET | `/posts/{publicId}/comments` | ✅ | 顶层评论列表 |
| POST | `/posts/{publicId}/comments` | — | 发表评论或回复 |
| POST / DELETE | `/posts/{publicId}/like` | — | 点赞 / 取消（幂等，返回操作后的状态与计数） |
| POST / DELETE | `/posts/{publicId}/favorite` | — | 收藏 / 取消（幂等） |
| GET | `/comments/{publicId}/replies` | ✅ | 某条顶层评论的回复 |
| DELETE | `/comments/{publicId}` | — | 删除评论（软删除，仅作者；顶层评论连带删除其回复） |
| GET | `/me/favorites` | — | 我收藏的帖子 |

新增错误码（`ErrorCode`）：`40030` 所选板块不存在 · `40031` 帖子内容不符合要求（超长 / 标签过多）·
`40032` 标签名不合法 · 以及社区侧统一使用的 `40400` 资源不存在。

参数处理策略**刻意不一致**，且不一致本身是设计：`page` / `size` 的非法值走"归一化"
（`page=0` 修正为 1、超上限截断），而 `sort` 走"拒绝"。前者的合法值是一个范围，
后者是一个有限集合 —— 集合外没有"合理的默认解释"。

## Security

- **读公开、写必须登录**，公开端点**逐条列出、默认拒绝**。新增接口时忘记加规则的结果是
  "访问不了"（立刻被发现），而不是"裸奔"（很久后才发现）。
- **内容注入面收敛**：正文由服务端渲染 + OWASP 白名单净化；**全前端仓库只有一处 `v-html`**，
  其值只能来自已净化的 `bodyHtml`。列表摘要与评论均以文本节点渲染，不进 HTML 路径。
- **评论按纯文本存储与渲染，不解析 Markdown**：评论区是数量级更高的内容入口，
  让可渲染的输出出现在那里等于把注入面放大到与正文同级。
- **归属校验统一返回 404 而非 403**，不泄漏"这条资源是否存在"。
- **演示数据生成器默认关闭**，显式拒绝在 `prod` profile 下执行；
  演示账号与口令**打印在启动日志里** —— 它是公开入口，不该表现得像个秘密。
- **令牌续期只对 `40101`（令牌过期）触发一次刷新重试**；`40100` / `40102` / `40104` 不重试 ——
  它们刷新解决不了，重试只会把用户困在必然失败的循环里。刷新令牌**并发去重**，
  因为服务端把"同一刷新令牌被用两次"视为泄露证据并撤销该账号全部会话。
- **修复了一处静默失效的安全配置**：`application.yml` 中 `request:` 块此前写在**顶层**，
  而属性类前缀是 `app.request`，于是整块安全开关（含 `APP_TRUST_FORWARDED_HEADERS`）
  全部失效 —— 表现为"限流在反向代理之后把所有请求都算在同一个代理 IP 上"。
  已修正并新增结构断言；**反向验证过**：还原成修复前的 yml 会报 11 个缺失键。

| 性质 | **基线测量**（不是优化对比），编号刻意用 `EX-000` 而非 §30.2 的对比模板 |
| 环境 | MacBook（Apple Silicon arm64）/ macOS 14.4，**单机**：应用与 MySQL 同机；MySQL 8.4 容器；**未启用 Redis** |
| 数据集 | 帖子 **2000** · 评论 **4000** · 互动 **18094** · 浏览记录 **10000** · 作者 20 · 板块 6 · 标签 15 |
| 方式 | HTTP 端到端、**并发 1**、每场景预热 30 次 + 测量 200 次；13 个场景、**2600 次测量、0 次失败** |

实测结果（p50 单位 ms）：

| 场景 | 认证 | p50 | p90 | p99 |
|---|---|---:|---:|---:|
| 板块列表 | 匿名 | 6.3 | 7.5 | 15.5 |
| 热门标签 | 匿名 | 8.0 | 8.6 | 10.0 |
| 信息流 第 1 页（默认最新） | 匿名 | 6.2 | 7.0 | 9.1 |
| 信息流 第 1 页（最热排序） | 匿名 | 5.8 | 6.8 | 14.6 |
| 信息流 第 1 页（板块筛选） | 匿名 | 5.1 | 5.9 | 8.2 |
| 信息流 第 1 页（标签筛选） | 匿名 | 6.1 | 6.9 | 8.4 |
| 信息流 第 10 页（深分页） | 匿名 | 5.7 | 6.5 | 8.4 |
| 帖子详情（匿名，不写浏览） | 匿名 | 3.0 | 3.7 | 4.5 |
| 顶层评论列表 | 匿名 | 4.0 | 4.7 | 5.2 |
| 信息流 第 1 页（带登录态，含 `liked` / `favorited`） | 令牌 | 7.7 | 8.5 | 18.1 |
| 帖子详情（带登录态，含浏览去重查询） | 令牌 | 5.3 | 5.9 | 6.7 |
| 我的收藏 | 令牌 | 6.8 | 7.9 | 9.1 |
| 某条顶层评论的回复列表 | 匿名 | 3.5 | 4.3 | 4.9 |

**结论：当前数据不支持引入缓存。** 判据不是"数字够不够小"，而是这份数字能不能指出一个具体的问题 ——
13 个场景全部落在 3.0~8.0 ms，没有任何场景达到"明显偏高"（即 N+1 或缺失索引）的程度。
最慢的"热门标签"（8.0 ms）是**聚合本身的工作量**：它要按被引用帖子数倒序取前 20 个标签，
聚合范围随帖子量增长，是本次唯一"随数据量线性变差"的候选，Phase 09 若要挑第一个优化对象，先看它。

**已知的高价值偏差**：假设"深分页应更慢"被观察到的是**不慢**（第 10 页 p50 5.7 ms，比第 1 页低 0.5 ms）。
这不代表深分页没问题，只代表 2000 帖 / `LIMIT 180,20` 这个规模还不足以让它显形 ——
结论是"现在不动它"，而不是"它不是问题"。

**局限（读这张表必须知道）**：① 并发为 1，**不能用来推算吞吐**；② 单机同机无网络跳转，
部署到跨机环境时参考价值明显下降；③ p99 与 max 只由约 2 个样本决定，可重复性较差；
④ 数据是合成的、分布均匀，**热点帖的读取成本未被覆盖**，而它往往最先出问题；
⑤ 只测读取不测写入；⑥ 没有 `EXPLAIN`，本记录回答"多快"不回答"为什么是这个速度"。

> 测量过程中还发现并记录了一个陷阱：`--logging.level.ai.camphub=INFO` **关不掉** mapper 的
> SQL DEBUG 日志（logger 名按具体到宽泛匹配），第一次测量因此数字偏高，逐个覆盖后才重测。

## Known Limitations

诚实列出，未完成的不写成已完成。

1. **净化白名单的修复不会自动作用于已落库的历史 HTML**（`body_html` 是写入时的快照）。
   处置路径是"重渲染回填"，`body_md` 已保留因此这一步是确定性的。见 `docs/adr/0005`。
2. **刷新令牌存 `localStorage`**：XSS 一旦发生可被取走长期凭据。正确收口是改为 `httpOnly` Cookie
   并补 CSRF 防护；当前压低风险的是"全仓库唯一一处 `v-html`，且内容由服务端净化"。
3. **浏览计数只统计登录用户**，匿名访问不计入，且同一用户同一天只计一次。
4. **深分页仍为 `LIMIT offset`**；**热度排序是"按点赞数倒序"**，没有时间衰减与多项加权。
   在这批数据上两者都还不痛，但都记在案。
5. **社区没有审核能力**：任何登录用户都能发布任意内容。审核域在 Phase 10。
6. **限流与登录失败计数为单进程内存实现**（Phase 02 遗留），多实例部署会失效。
7. **Windows 可移植性**：构建入口（Maven Wrapper / npm scripts / Docker Compose）本身平台无关，
   测量脚本只用 Node 内置能力；但**尚未在真实 Windows 上验证**，规约 §18.6 要求的
   "不得把未验证的适配写成已验证"在此遵守 —— 当前状态是「已在 macOS 实测」。
8. **无搜索能力**：社区只有板块 / 标签 / 排序 / 分页，没有关键词检索。检索域在 Phase 06。

## Technical Debt

| 项 | 性质 | 偿还时机 | 触发条件 |
|---|---|---|---|
| `GET /tags` 全表聚合 | 唯一随帖子量线性变差的读路径 | Phase 09 | p95 > 50 ms 或帖子量 > 10 万 |
| 深分页 `LIMIT offset` | 固有代价，当前未显形 | Phase 09 | offset > 1 万，或某筛选下 p95 > 50 ms |
| 带登录态信息流每行两个子查询 | 随页大小线性增长 | Phase 09 | 页大小调大，或 +24% 变成倍数 |
| 历史 `body_html` 无回填机制 | 需要时手工执行 | 净化规则发生安全级变更时 | 白名单收紧 |
| 刷新令牌在 `localStorage` | 已知风险，已用"唯一 `v-html`"压低 | Phase 04（引入 Workspace 权限模型时一并评估 Cookie 方案） | 需要一个统一的前端凭据策略 |

| 演示数据生成耗时 131 秒 / 2000 帖 | 走公开应用服务是有意为之（代价换真实性） | 不需要偿还 | 这是设计选择，不是债 |

**不列入技术债的**：没有缓存、没有消息队列、没有审核——它们是**本阶段刻意的范围边界**，
有 ADR 或阶段计划作为依据，不是"欠下的"。

## Next Phase Dependencies

Phase 04 — Workspace & Resource Authorization 依赖本阶段交付的以下前提：

1. **已鉴权身份**（Phase 02）：所有写操作建立在"请求一定带有已鉴权身份"之上，社区写入路径已按此实现。
2. **内容与资源分离的边界**：本阶段建立了"公开内容（Community）"一侧；
   Phase 04 引入的 Workspace（私有内容）必须复用同一套渲染与净化边界（`MarkdownRenderer`），
   但**权限过滤必须前置到检索阶段**，而不是检索后再过滤输出。
3. **模块边界断言可扩展**：`ModuleBoundaryTest` 已用 ArchUnit 钉住现有模块依赖方向；
   新增 `workspace` 模块时，边界规则需同步扩展，而不是靠评审自觉。
4. **私有内容绝不自动公开**：本阶段确立了"发布必须显式确认 + 预览 + 可撤回"的对外承诺模板，
   Phase 04 的 Workspace → Community 发布路径必须实现它，不能在实现时降级为"默认公开"。
5. **计数与幂等的既有模式可直接复用**：`(user_id, target_id, type)` 主键保证幂等、
   计数内联在内容表（ADR 0004）这两个决定，在 Workspace 的收藏 / 协作场景下同样适用。
6. **前端凭据策略待统一**：本阶段把令牌放在 `localStorage`，Phase 04 引入更细的资源授权后，
   需要在同一轮评估是否改为 `httpOnly` Cookie（见 Technical Debt）。
