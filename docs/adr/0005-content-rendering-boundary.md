## Context

Phase 03 第一次让**用户自由撰写的内容**进入系统。在这之前，所有对外输出都是服务端拼的字符串，
不存在"内容里藏着标记"的问题。从这一阶段开始，有三个必须一次性定下的问题：

1. **库里存什么？** 只存 Markdown 原文？只存渲染后的 HTML？还是两者都存？
2. **在哪里把 Markdown 变成 HTML？** 服务端，还是交给客户端？
3. **评论要不要也支持 Markdown？**

这些问题一旦有内容沉淀就极难回头：

- 存了 HTML 再想改回存 Markdown，需要把历史 HTML 反向解析回 Markdown ——
  而反向解析**没有唯一解**（`<br>` 是空行还是换行？`<strong>` 是 `**` 还是 `__`？），
  结果是历史内容与新增内容的形态永久性不一致。
- 渲染点一旦同时存在于服务端与客户端，就有了**两个净化实现**，
  而它们必然在某次升级中分叉：一边修了新的 XSS 载体，另一边没有。

同时有一个具体的威胁需要在这一阶段就堵住：帖子正文最终要以 HTML 显示在别人的浏览器里，
这正是存储型 XSS 的经典入口。

另外还有一个已经存在的约束会影响选择：**列表页不读 `MEDIUMTEXT` 正文**。
列表每页 20 行，为取摘要而把整列正文读出来，会让最热的读路径变成最重的读路径
（这一条在 `V3__community.sql` 里已作为索引与列设计的依据写定）。
它意味着**摘要必须在写入时就从正文派生并落库**，不可能"读时再算"。

## Decision

### 决策一：**Markdown 原文是编辑的事实来源，渲染结果随写入落库**

`post.body_md` 保存 Markdown 原文，`post.body_html` 保存**写入时**渲染并净化的 HTML。
两份由 `PostService` 的**单一写入口**（`create` / `update` 各一处）一起更新。

### 决策二：**渲染与净化只在服务端做，且只在一个类里做**

`community/domain/MarkdownRenderer` 是唯一的渲染入口（commonmark + OWASP Java HTML Sanitizer），
同时负责渲染与白名单净化。前端拿到已净化的 `bodyHtml` 直接插入，
**不做二次渲染、不做二次转义**。

### 决策三：**摘要也在写入时从 Markdown 原文派生**（`MarkdownRenderer.summarize`，
基于 commonmark 的 `TextContentRenderer`），而不是在 HTML 上剥标签 ——
剥标签会把代码块与表格的内容混进摘要。

### 决策四：**评论不是 Markdown，而是纯文本**

`comment.body` 只存纯文本（保留换行），前端以文本节点渲染。评论不提供 Markdown 能力。

### 配套规则

1. **`body_html` 永远不对用户输入"透传"**。净化失败时渲染器抛错（→ 500 + traceId），
   绝不降级为"原样输出"。任何"净化出错就放过"的兜底都等于计划外敞开。
2. **前端全仓库只允许一处 `v-html`**（`PostDetailView.vue`），其值只能来自 `bodyHtml`。
   新增任何 `v-html` 都应视为需要评审的改动。列表摘要以文本节点渲染。
3. **`bodyHtml` 是服务端承诺的信任边界**。将来若出现第二个消费方（邮件渲染、导出、
   第三方接口），它必须走同一个渲染器，不允许自己拼 HTML。
4. **两份内容必须一起更新**，并由集成测试断言（改完正文后 `bodyHtml` 随之变化），
   而不是靠"每个开发者记得改两处"。

## Alternatives

### 备选 A：只存渲染后的 HTML（不保留 Markdown）

**得到**：读路径最省事，不需要渲染；存储只有一份，不可能不同步。

**代价**：
- **编辑无法精确往返**：把 HTML 反向解析回 Markdown 没有唯一解，用户会看到自己的
  排版在每次编辑后发生细微变化；
- **净化策略的修复无法通过升级代码生效**：今天放行的标签明天被发现有新的利用方式时，
  已经写进库的危险标记不会因为部署了新版本而消失，必须回写全表 ——
  而在回写期间那些内容仍然是危险的；
- **渲染规则永久冻结**：换 Markdown 方言、修一个列表嵌套错误、加代码高亮，
  历史内容都不会跟着变，库里逐渐变成"按十几个渲染器版本渲染出来的拼贴画"。

**否决理由**：它把"每次读取省一次渲染"换成了"渲染规则与净化策略永久冻结"。
后者的代价与安全属性相关，不对等。而且它丢掉了 `body_md`，
**使得将来的任何调整都失去依据** —— 这是本决策最不能接受的一点。

### 备选 B：只存 Markdown 原文，每次读取时渲染

**得到**：
- 没有冗余列，不存在"两份不同步"这个故障模式；
- 渲染规则与白名单可以随时演进，历史内容自动跟随；
- 存储更小。

**代价**：
- 每次读详情都要渲染一次；
- **列表摘要也必须在读取时计算** —— 这与"列表页不读 MEDIUMTEXT 正文"直接冲突：
  要么违反那条约束，要么每次读列表都为 20 行做 20 次渲染。

**这个备选没有被"安全"否决，而是被"摘要的存放位置"否决了。**
Phase 03 已经确定摘要必须预先派生（否则列表要么读正文、要么每行渲染），
既然写入路径上已经必须为摘要解析一次 Markdown，**在同一个地方顺手渲染出 HTML
的边际成本几乎为零**；反过来，选备选 B 就意味着把"解析 Markdown"这件事
同时留在写路径（算摘要）与读路径（渲染 HTML）两处。

**若将来实测显示"写入时的渲染"成为发布路径瓶颈**，正确的调整是把渲染挪到异步
（Phase 05 起会有任务与状态机的框架），而不是改成读时渲染。

### 备选 C：客户端渲染

**得到**：可以直接做"所见即所得"的实时预览，编辑体验最好。

**代价**：净化逻辑要在 Java 与 JS 两处维护，两套白名单不可能长期一致；
最终 HTML 由浏览器生成，服务端无法对输出负责；需要把 Markdown 解析库打进前端产物。

**否决理由**：XSS 的防线数量翻倍，而整体强度取决于最弱的那一环。

### 备选 D：评论也支持 Markdown

**得到**：评论排版能力更强，与正文体验一致。

**代价**：
- 评论区是**数量级更高**的内容入口，也是垃圾信息与注入尝试的主要落点，
  让评论可渲染等于把该入口的威力放大到与正文同级；
- 评论通常很短，代码块/表格这类真正需要 Markdown 的场景极少出现；
- 一旦支持，立刻出现"为什么这条评论允许 `<a>` 而那条不允许"这类策略问题 ——
  正文与评论需要不同的白名单。

**否决理由**：收益（短文本的排版）远小于成本（注入面与策略复杂度）。
将来若要支持，必须为评论维护一份**独立且更严格**的白名单，而不是复用正文那份。

## Consequences

### 正面

- **读路径零渲染成本**：列表与详情都是一次 `SELECT`。
- **XSS 只有一条防线、只有一份实现**：审计时只需读 `MarkdownRenderer` 与
  `PostDetailView` 两处，而不是"所有渲染过内容的地方"。
- **保留了演进空间**：因为 `body_md` 在，渲染规则或白名单的升级可以通过
  **一次性重渲染回填**作用到历史内容 —— 这正是与备选 A 的本质区别。
- **编辑是精确往返**：编辑器 `v-model` 绑定的就是入库的那份文本。
- **检索与 RAG 拿到的是干净原文**（Phase 07 / 08 直接受益）：
  索引 Markdown 原文而不是 HTML，命中高亮与片段抽取不需要先剥标签；
  将来的切块与引用定位也在原文上做，引用信息更准确。

### 负面 / 代价

- **存储冗余**：HTML 通常比等价的 Markdown 大，且两份可能不同步。
  缓解手段是单一写入口 + 集成测试断言。
- **⚠️ 净化白名单的修复不会自动作用于历史内容。** 这是本决策最需要在意的代价：
  存量 `body_html` 是按旧白名单渲染的。发现新的 XSS 载体时，
  部署新版本只能保护**此后写入**的内容。
  **处置路径是"重渲染回填"**（因为 `body_md` 在，这一步是确定性的），
  而不是"临时在读取路径上加过滤"—— 后者会让读取路径也长出一份净化逻辑，
  正好回到备选 C 的问题。
  **该代价有一个需要明确的时间窗**：白名单修复发布到回填完成之间，
  历史内容仍按旧规则呈现。
- **没有实时预览**：用户对排版没有即时反馈。这一点在编辑页被**明确告知**
  （"渲染与内容净化在服务端完成，因此这里不提供实时预览"），
  而不是让用户提交后才发现排版不对。
- **`v-html` 这个可疑写法会长期存在于代码里**：只能靠注释与规则维持
  "只此一处、来源可信"这条约束，需要纪律成本。

### 中性但有长期影响

- **白名单的每一次放宽都是安全决策**，必须在 diff 中可见并说明理由。
  当前刻意不放行代码块的 `class`（没有语法高亮时，放行只会让人能写入任意 `class`
  去试探样式边界）。
- **将来引入富文本编辑器时会与本决策冲突**。届时若确实需要 WYSIWYG，
  应当存"结构化文档模型"并新增 ADR，而不是改成本决策的备选 A ——
  结构化模型仍然保留"渲染规则可演进"这个关键属性。

## 复核触发条件

1. **发现新的 XSS 载体、需要让历史内容也立即见效** —— 触发重渲染回填，
   并评估是否需要把净化移到读取路径（届时需重写本 ADR）。
2. 实测显示写入时的渲染成为发布路径瓶颈 —— 评估把渲染挪到异步任务。
3. 出现正文之外的第二类需要渲染的富内容（例如 Phase 05 的文档解析结果）——
   必须明确它是否复用本渲染器与白名单，或另建一条边界。
4. 引入富文本编辑器 —— 评估结构化文档模型。

**在此之前，本决策冻结。**
