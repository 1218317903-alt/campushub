## Context

Phase 01 需要定下一个**跨前后端的、后续所有接口都要遵守**的响应约定。这个约定的特点是：
**改起来极贵** —— 一旦前端、测试、文档、后续十余个模块都按它写，之后修改等于全项目返工。

需要解决的具体问题：

1. 前端要为每个接口写一套错误处理，无法统一。
2. 用户报障时说「操作失败了」，没有任何可定位的信息。
3. 表单接口需要把错误定位到具体字段，而不是弹一句「参数错误」。
4. 框架自身抛出的异常（404、405、415、反序列化失败）默认响应格式各不相同，
   与业务异常混在一起，前端需要写多套分支。
5. 5xx 有泄漏内部实现细节（堆栈、SQL、类名）的风险。

同时有一个容易被忽略的诱因：**如果成功响应也套信封，很多问题看起来会被「整齐地」解决** ——
`{code, data, message}` 看起来统一了。所以这个备选必须被认真对待。

## Decision

**错误响应使用结构化信封；成功响应直接返回业务数据本身，不套信封。**

### 错误响应契约（冻结）

```json
{
  "code": 40400,
  "message": "资源不存在",
  "traceId": "3f1a9c2e4b7d4f1a8e6c0b2d5a7f3e91",
  "timestamp": "2026-09-17T08:00:00Z",
  "path": "/api/v1/posts/123",
  "details": [{ "field": "title", "reason": "不能为空" }]
}
```

错误码为 5 位数字，编码规则 `HHH SS`（HTTP 状态码 + 该状态内的序号），
例如 `40400` = HTTP 404 的第 0 号错误。序号段按模块预分配，防止各模块撞号。

### 配套的四条规则

1. **`details` 恒为数组，从不为 `null`。** 前端可以无条件遍历。
2. **所有失败响应都必须是这个形状**，包括框架抛出的异常（404/405/415、参数绑定失败、
   请求体不可读、媒体类型不支持）。由 `GlobalExceptionHandler` 统一收口。
3. **5xx 绝不泄漏内部细节。** 兜底分支只返回固定文案 + traceId，堆栈只进日志。
4. **链路 ID 走响应头 `X-Trace-Id`**，覆盖所有响应（含成功）。

前端把该结构映射为 `ApiError` 类，并提供 `fieldMessages()` 直接产出可绑定到表单的
`{ 字段名: 提示 }`；同时把「服务端返回了结构化错误」（`ApiError`）与
「连不上 / 超时 / 响应不是 JSON」（`NetworkError`）区分为两个类型。

## Alternatives

### 备选 A：统一信封 —— 成功与失败都返回 `{code, message, data}`

**得到**：
- 前端只需要判断 `code`，不用依赖 HTTP 状态码；
- 表面上「所有响应形状一致」，看起来更整齐。

**代价**：
- **HTTP 状态码失去意义**。若所有响应都是 HTTP 200，CDN、网关、负载均衡、监控、
  浏览器 DevTools、`curl -f`、以及一切基于状态码的工具链都看不到失败。
  等于把协议层已经提供的语义**扔掉再自己发明一遍**。
- **成功响应多一层无信息量的包裹**。`data` 这一层不承载任何信息，
  但它出现在每一个接口、每一个类型定义、每一处解包代码里。
- **OpenAPI 文档的 schema 多一层缩进**，生成的客户端类型也多一层泛型 ——
  成本按接口数量线性累积。
- 错误需要的元信息（错误码、traceId、字段明细）在成功响应里**根本不存在**，
  所谓「形状一致」其实是拿一堆 `null` 占位，并不真的统一。

**否决理由**：它把「错误的额外元信息」这个真实需求，错误地推广成了「所有响应都需要信封」。
正确的读法是：**错误需要结构，是因为错误携带额外信息；成功没有额外信息，所以不需要。**

### 备选 B：成功也无信封，但错误用 HTTP Problem Details（RFC 9457）

**得到**：标准化的错误格式（`type` / `title` / `status` / `detail` / `instance`），
Spring Boot 内置 `ProblemDetail` 支持，跨语言生态认知度更高。

**代价**：
- 需要把「业务错误码」塞进 `type`（URI）或扩展字段，语义被迫扭曲 ——
  `type` 设计为指向错误类型文档的 URI，而我们的错误码是一个用于**程序判断**的整数；
- 中文文案、字段级明细（`details`）仍需作为扩展字段加入，即最终格式与自定义结构并无实质差异；
- 与规约中已经写定的错误码体系（5 位、按模块分段）需要额外一层映射。

**否决理由**：这是个**好标准，但对本项目的错误码体系是多余的中间层**。
错误码是本项目的核心契约（前端按码分支、按段分配），强行套 RFC 9457 只会让每个错误
都要维护一份「业务码 ↔ type URI」的映射，收益不抵成本。

### 备选 C：不定义契约，各模块自行返回错误

**得到**：每个模块可以按自己的语义返回，短期自由度最高。

**代价**：前端需要为每个接口写一套错误处理；
「用户报障 → 定位问题」这条链路在每个模块都要重新设计一次；
后续新增模块时错误格式必然漂移。

**否决理由**：它是备选 A/B 都不选之后的默认结果，而这个结果就是当前要解决的问题本身。

## Consequences

### 正面

- **前端只需实现一套错误处理**，并在 `http.ts` 一处完成类型映射。
- **用户报障可定位**：错误响应里的 `traceId` 与后端日志中的 `traceId` 一致，
  报来一个 ID 就能捞出该请求的全部日志。前端错误提示中直接展示它。
- **表单错误可定位到字段**：`details` 支持 `{field, reason}`，前端 `fieldMessages()`
  可直接绑定到表单控件，不需要解析字符串。
- **HTTP 语义完整**：状态码如实反映结果，网关/监控/浏览器工具链正常工作。
- **5xx 不泄漏实现细节**：避免通过报错信息枚举出类名、表名、SQL、依赖版本。
- **成功响应轻量**：前端少一层解包，OpenAPI schema 少一层缩进，接口数量增长时收益线性放大。
- **契约可测试**：`ErrorContractIT` 断言 404/405 的统一性、traceId 一致性、
  入站 traceId 透传、以及 500 响应中不含内部细节。

### 负面 / 代价

- **前端需要依赖 HTTP 状态码判断成败**（`response.ok`），而不是只看 body 里的 code。
  这实际上是**返回到了 HTTP 的本意**，但对习惯「全 200」风格的人是心智转换。
- **不能只靠 HTTP 状态做业务分支**：同一状态码下可能有多个业务错误码（如 400 段有
  40000~40003），前端仍需读 `code`。**两者都要用，各司其职**：
  状态码用于传输层判断，业务码用于业务分支。
- **需要在框架层做统一收口**，否则会出现「漏网的默认错误格式」。
  这部分工作集中在 `GlobalExceptionHandler`，且已被集成测试覆盖 —— 属于一次性成本。
- **`traceId` 与 `timestamp` 由服务端生成**，因此错误响应的构造必须经过统一的工厂方法
  （`ApiError.of(...)` / `withDetails(...)`），不能手工 new。这是需要靠约定维持的纪律。

### 中性但有长期影响

- **错误码一旦发布，应视为契约**。删除或改变某个码的含义会破坏前端分支逻辑。
  新增模块时先在本 ADR / `ErrorCode` 的序号段表中登记，再使用。
- **规约允许「无权访问时对外表现为 404」**（`ErrorCode.NOT_FOUND` 的注释已写明），
  目的是避免通过错误码差异推断资源是否存在。这是错误契约与安全策略的交汇点，
  后续实现资源级鉴权（Phase 04）时必须遵守。
- 后续若引入 RFC 9457 或其他标准，应新增 ADR，而不是就地修改本契约。

---

## 复核触发条件

1. 出现第三方调用方（开放 API、SDK、外部集成），需要提供标准化错误格式。
2. 错误码体系出现无法承载的新语义（例如需要携带重试建议、需要多语言文案）。
3. 前端出现必须在 envelope 层解决的横切需求（目前未见到）。

**在此之前，本契约冻结。**
