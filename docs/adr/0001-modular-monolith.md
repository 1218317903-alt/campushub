## Context

CampusHub AI 需要承载的业务域包括：用户与权限、Workspace 协作、社区内容、外部数据采集、
搜索、RAG 与 Agent、通知、审核、后台。从数量上看，「服务很多」，很容易得出「应该上微服务」的结论。

但需要先看清**复杂度究竟来自哪里**：

1. **业务域多** —— 模块边界需要清晰。
2. **异步链路长** —— 文档解析、采集、索引、AI 生成都是长任务。
3. **权限要求高** —— 私有内容不能泄漏，资源级鉴权必须前置到检索阶段。
4. **流量未知** —— 目前没有任何真实用户与负载数据。

这四条里，**没有一条是「需要多个部署单元」**。

同时存在两个硬约束：
- 单人开发，没有独立的运维/SRE 角色；
- 十多个仓库的 CI/CD、服务发现、配置中心、分布式追踪配置，会挤占本该用于业务功能的全部精力。

## Decision

采用 **Modular Monolith**：单一部署单元、单一数据库，但**模块边界在代码层严格落地**，
并由构建期断言强制维持。

关键是「边界靠什么维持」，而不是「边界画在哪里」。因此本决策包含**不可分割的两部分**：

**① 包结构与依赖方向**
- 模块按**业务域**划分（`identity` / `workspace` / `community` / …），模块内部分 `api` / `app` / `domain` / `infrastructure` 四层。
- 模块间**禁止跨模块访问对方的数据表**；跨模块的写操作走**领域事件 + outbox**（Phase 05 起）。
- `common` 是共享内核，只能被依赖，不能依赖任何业务模块。

**② 边界由构建期断言守护**（`src/test/java/ai/camphub/architecture/ModuleBoundaryTest.java`）
用 ArchUnit 在 `mvn test` 阶段强制以下规则，**越界直接让构建失败**：

| 规则 | 拦住的问题 |
|---|---|
| 模块间无循环依赖 | 边界名存实亡，后续无法拆分 |
| `common` 不依赖业务模块 | `common` 退化成「万能垃圾桶」 |
| `..api..` 不依赖 `..infrastructure..` | 绕过权限校验与事务边界 |
| `..domain..` 不依赖 `org.springframework..` | 领域逻辑被框架渗透，无法脱容器测试 |
| `@RestController` 必须在 `..api..` | 上述规则因包名不匹配而失效 |
| 禁止 `@Autowired` 字段注入 | 依赖不可见、对象无法在容器外构造 |

包名模式使用通配（`..api..` / `..domain..`），新增模块时**无需修改测试**，规则自动覆盖。

> ②才是本 ADR 的核心。①只是画线；没有②，三个月后一次「先这样调用一下」的临时跨模块访问
> 就会让①名存实亡，而那时的拆分成本已经回到起点。

## Alternatives

### 备选 A：从一开始就拆微服务

**得到**：独立部署、独立扩容、故障隔离、技术异构。

**代价**：
- 分布式事务 / 最终一致性心智负担 —— 而本项目跨模块写场景（如「帖子发布 → 更新统计 → 写索引 → 发通知」）用本地事务 + 事件就能干净解决；
- 十余个仓库的 CI/CD、服务发现、配置中心、分布式追踪配置；
- 跨服务调试从「打断点」变成「拼日志」；
- 单机资源被十余个 JVM 瓜分，实际吞吐反而更低。

**否决理由**：在没有真实负载数据时拆服务，是在为**想象中**的问题支付**确定**的成本。
而 Modular Monolith 已经能拿到微服务的约 80% 好处。

### 备选 B：不分模块的传统单体（按技术分层：controller / service / dao 全局各一层）

**得到**：上手最快，前期写代码无需思考模块归属。

**代价**：
- 依赖关系变成任意交叉，改动影响面无法推断；
- 没有边界，也就**没有未来拆分的抓手** —— 想拆时面对的是一个已经长成的大泥球；
- 权限这类横切关注点容易被某一条链路漏掉，且没有结构性手段发现它。

**否决理由**：它省下的是前期的一点思考成本，换来的是后期无法偿还的结构债。
而且它并不比 Modular Monolith 少写代码 —— 只是少写一个包名前缀。

### 备选 C：Modular Monolith，但不加架构测试

**得到**：少写一个测试类，不引入 ArchUnit 依赖。

**代价**：边界退化成「文档里的约定」。而约定无法在代码评审时被可靠检查 ——
评审者不会记得每条依赖方向，CI 更不会。

**否决理由**：把架构决策变成可执行断言的成本极低（一个测试类），收益是长期的。
**决策一旦写下就必须能自动维持**，否则它只是愿望。

## Consequences

### 正面

- **单一进程**：本地起一个后端即可开发、调试、断点；无需服务发现与跨服务追踪。
- **单一数据库 + 本地事务**：跨模块写操作用 ACID 事务即可，不需要处理分布式一致性。
- **边界清晰**：模块职责与依赖方向明确，新成员看包结构就能理解系统。
- **拆分成本低**：未来若某个模块确需独立部署（如 `ai` 模块受模型调用延迟影响需单独扩容），
  因为边界已经干净，抽取成本远低于从大泥球中剥离。
- **权限可前置**：模块化的应用服务层是权限判定的天然位置，避免权限散落在 Controller 里。

### 负面 / 代价

- **必须在包名与依赖方向上保持纪律**：违反会被构建拦下，需要花时间改对而不是「先合进去」。
  这是刻意选择的摩擦。
- **异步与长任务需要额外设计**：单进程内需要自己处理任务调度、重试、幂等（Phase 05 起）。
  但这部分复杂度在任何架构下都存在，微服务只是把它转移到了消息中间件。
- **进程级角色分离需要手动配置**：`api` / `worker` / `scheduler` 需要靠 Spring Profile 或启动参数区分，
  而不是天然由部署单元区分。
- **数据库共享意味着无法独立演进 schema**：各模块的表结构变更需要考虑对其他模块的影响，
  因此**跨模块直接读对方的表是被禁止的** —— 这条约束必须被严格遵守，否则耦合会从代码层转移到数据层。

### 中性但有长期影响

- **引入新中间件需要先有数据支撑**（`00-工程规约.md` §16）。
  这是本决策的配套约定：Modular Monolith 不意味着「什么都往单体里塞」，
  而是「先证明需要，再引入」。
- **模块边界的正确性需要随业务演进重新评估**。本 ADR 不认为当前划分是终局；
  划分调整时应新增 ADR 记录，而不是悄悄改包名。

## 复核触发条件

出现以下任一情况时，应重新评估本决策并新增 ADR：

1. 某个模块的资源画像与其余模块显著不同（例如 `ai` 模块需要 GPU 或需要独立扩容）。
2. 单进程部署无法满足可用性要求（需要故障隔离）。
3. 团队规模增长到需要多个独立交付单元并行推进。
4. 出现必须由不同技术栈实现的模块。

**在此之前，不拆。**
